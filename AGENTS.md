# hasquant

Haskell bindings to QuantLib via c2hs, with a C++ shim layer in `cbits/`.

hasquant binds QuantLib's C++ API directly; it does not depend on QuantLib-SWIG. A QuantLib-SWIG reference is prior art for an API-shape decision, not an implementation dependency.

## Before inventing a workaround

Before adding a hand-rolled enum mirror, module, or abstraction, search this file, the codebase, and `.claude/skills/` for the existing pattern. Reuse it: c2hs enum imports, secondary interfaces, and wide constructors have non-obvious safety constraints. Cross-cutting enums belong in `QuantLib.Internal.Common` to avoid import cycles.

## Skills

`.claude/skills/` (grep it and this file before inventing a workaround, per above):

**Adding a binding**
- `add-quantlib-class` — bind a whole new QuantLib C++ class (hierarchy root or new member of an existing one), shim + Haskell layer.
- `add-quantlib-method` — bind one more method/getter onto a class that's already bound.
- `add-quantlib-adt` — decide enum vs. live object vs. nested-ADT (Payoff/Exercise-style) for a new value type, and build the nested-ADT case.
- `add-quantlib-options-record` — TH-generated options-record entry point for a constructor/method with >10 trailing defaulted params.
- `add-quantlib-index` — add or reconcile an Ibor/overnight/swap index binding.

**Build, test, platform**
- `run-hasquant` — build, run the test suite, and smoke-test a binding end-to-end.
- `build-windows` — build and test natively on Windows (GHC 9.10.3 + MSYS2).

**Reference**
- `c2hs-shim-patterns` — c2hs pragma flags, C shim marshalling patterns, and gotchas for `.chs`/`cbits/` work.

**Reconciliation audits**
- `reconcile-calendars` — sync the calendar enum against installed QuantLib's countries/markets.
- `reconcile-currencies` — sync the currency enum against installed QuantLib.
- `reconcile-daycounters` — sync the day counter enum and `BusinessDayConvention` against installed QuantLib.

## Build and test

See `run-hasquant` for build/test commands, the GHC 8.10 gate, allocation tracing, and smoke-test upkeep.

**Test placement:** put product, pricing, and behavioral regressions in CI-run Hspec tests under `test/hspec/`. ## API design

- **When adding a new binding, consider a neighboring one if it's low-effort and doesn't context-switch.** Minimalism (bind only what's asked) is still the default, but a sibling that reuses plumbing you just built — same marshalling shape, same fixture, same header already open — is often nearly free. `InterpolatedSwaptionVolatilityCube` alongside `SabrSwaptionVolatilityCube` is the model: it reused every piece of the SABR cube's `Handle`/tenor/`Matrix`/`SwapIndex` marshalling and needed no new infrastructure. If the neighbor needs its own investigation, its own fixture, or a genuinely different marshalling shape, it's a separate task.
- **Avoid `dynamic_cast`/`dynamic_pointer_cast` in `cbits/` unless upstream forces a downcast.** Prefer a concrete Haskell leaf type with concrete getters. Derived-to-base upcasts are safe; base-to-derived casts are the concern.
  - **The fix is usually "promote the accessor's return type to a real family, one more `AnyOf` layer deep" — not a cast at the point that needs the concrete type.** `SwaptionHelper::underlying()`/`swaption()` are `SwaptionHelper`-specific (not on the `BlackCalibrationHelper` base), and `swaptionHelper`'s own C++ shim already knows it is constructing a real `SwaptionHelper` — so instead of erasing to generic `BlackCalibrationHelper` at construction and `dynamic_pointer_cast`-ing back for these two getters, `SwaptionHelper` was made a real one-`AnyOf`-layer-deeper leaf under `BlackCalibrationHelper` (mirrors `GenMultiAssetOption`/`MargrabeOption` under `GenOption`, and `GenSwap`/`VanillaSwap` under `GenInstrument`): `type GenBlackCalibrationHelper bch = GenCalibrationHelper (AnyOf CBlackCalibrationHelper' bch)`, `BlackCalibrationHelper = GenBlackCalibrationHelper CBlackCalibrationHelper`, `SwaptionHelper = GenBlackCalibrationHelper CSwaptionHelper`. `underlying`/`swaption` then take the concrete `SwaptionHelper` pointer directly — genuinely cast-free, since the object handed to the C shim already *is* a `SwaptionHelper`, not something erased that needs rediscovering. The pre-existing base-level accessors (`times`, `blackPrice`, `impliedVolatility`, `marketValue`, `modelValue`, `setPricingEngine`, and the new `volatility`) were generalized from the concrete `BlackCalibrationHelper` to `GenBlackCalibrationHelper bch` so they keep working on `SwaptionHelper` (or any future leaf) without an explicit upcast at the call site.
  - **Root vs. leaf peek differs even after this promotion, and getting it backwards produces a confusing double-upcast, not a compile error.** A family *root at its own concrete type* (`BlackCalibrationHelper` used as itself, `MultiAssetOption` used as itself) peeks with `newCastForeignPtr` (no upcast — the C shim already erased to exactly that type at construction). A *leaf* one level under it (`SwaptionHelper`, `MargrabeOption`, `VanillaSwap`) peeks with `newGenForeignPtr` (upcasts via `Upcastable` on access). Promoting `BlackCalibrationHelper` from "leaf directly under `CalibrationHelper`" to "root of its own one-`AnyOf`-layer family" flips its own peek function from `newGenForeignPtr` to `newCastForeignPtr` — easy to miss since both compile either way (the extra/missing upcast just silently walks one hierarchy level too far or not far enough at runtime). `peel` count follows the same root/leaf split: a root's own `with*`/`peekPtrArray`-style array helper needs `peel` for each `AnyOf` layer already under it (`withBlackCalibrationHelperArray` needed 1 `peel` once `BlackCalibrationHelper` itself moved from 0 layers to 1); a same-depth leaf uses the identical `peel` count as the root, differing only in which concrete type occupies the innermost slot (`VanillaSwap` and `FixedVsFloatingSwap`-as-itself both need 2 `peel`s under `GenInstrument`, matching `MargrabeOption`/`MultiAssetOption`'s existing 2).
  - **An upstream accessor returning a *different* base than the one your leaf currently upcasts to is the other trigger for widening a family**, independent of any cast question. `SwaptionHelper::underlying()` returns `FixedVsFloatingSwap`, not `VanillaSwap` — `VanillaSwap` upcast straight to `Swap` before this, collapsing the intermediate C++ level (the normal, correct default per "don't mirror the hierarchy 1:1"). Getting `underlying()`'s real return type bound at all meant giving `FixedVsFloatingSwap` the same one-more-`AnyOf`-layer treatment (`GenFixedVsFloatingSwap f = GenSwap (AnyOf CFixedVsFloatingSwap' f)`, `VanillaSwap = GenFixedVsFloatingSwap CVanillaSwap`) and moving `VanillaSwap`'s own inherited getters (`fairRate`, `fairSpread`, `fixedLeg*`, `floatingLeg*` — all genuinely declared on `FixedVsFloatingSwap` upstream, not `VanillaSwap`) to take `GenFixedVsFloatingSwap f` generically, exactly mirroring the `BlackCalibrationHelper` move above. `FixedVsFloatingSwap` itself binds no constructor (pure-virtual `setupFloatingArguments` upstream), so it only ever appears as an accessor return type or an upcast target — that's still enough to need the full family machinery, not just a type alias.
  - **A C++ return type erased *by upstream itself*, before your shim ever sees it, cannot be recovered by any of the above — check this before promising an accessor.** `NonstandardSwaption::calibrationBasket` returns `vector<shared_ptr<BlackCalibrationHelper>>`; `basketgeneratingengine.cpp` always constructs `SwaptionHelper` internally, but the erasure to the base already happened inside QuantLib's own code before the vector is returned, so basket elements are genuinely, only `BlackCalibrationHelper` by the time hasquant's shim wraps them — `underlying`/`swaption`/the `SwaptionHelper` leaf type are reachable only for helpers hasquant itself constructs (`swaptionHelper`/`swaptionHelperFromDate(s)`), never for basket elements. Confirm this by reading the upstream `.cpp` (not just the header) for the concrete type actually constructed, before assuming a cast — dynamic or `static_pointer_cast` — could close the gap; here it's not a cast problem, it's a fact about what information upstream already discarded.
- **Don't mirror QuantLib's C++ hierarchy 1:1.** A bound class with no calculations of its own, never needed as an argument type elsewhere, doesn't need a Haskell object/pointer type — a constructing function returning the parent (or grandparent) is enough. That's already how pricing engines work: `discountingSwapEngine`, `blackCapFloorEngine` etc. all return the generic `PricingEngine`. Introduce a dedicated type only when the class has its own calc/getter (`FxForward`'s `fairForwardRate`, `ForwardRateAgreement`'s `forwardRate`) or must be passed around as its own type. Same idea one level down: don't bind a constructor for a class whose constructors only delegate to a more complex one with no logic of their own (QuantLib's `FixedVsFixedSwap`-style thin convenience subclasses) — bind straight through to what it actually constructs.
- **Module placement follows the topical family, not C++ inheritance.** `FxForward` lives in `QuantLib/Instrument/Forward.chs` alongside `ForwardRateAgreement`/`BondForward`, though it isn't a C++ `Forward` subclass. Leave the generic root module (e.g. `QuantLib/Instrument.chs`) for hierarchy-wide methods.
- **Bind few inspectors** — only what scheduling/pricing/output needs. `Schedule` binds `dates` out of ~20 upstream inspectors, `Calendar` binds none of its 4 (`empty()`/`name()`/`addedHolidays()`/`removedHolidays()`), `Currency` a curated 5 of 10. Prefer one targeted getter (as with `FxForward`'s `fairForwardRate`/`npvSourceCurrency`/`npvTargetCurrency`) over binding everything the C++ class exposes.
- **Setters** exist only for engine/pricer wiring (`setPricingEngine`, `setCouponPricer(s)`), the global `Settings` singleton, and `SimpleQuote.setValue` (mutable by design) — not as general field mutators. Prefer constructing a new object over mutating one (bake a flag into a constructor rather than adding a post-construction setter). **Confirm with the user before adding any new setter/mutator**, even mid-exploration — don't rely on self-judging it against this rule.
- **Typeclasses** are fine, even normal, as *internal* plumbing — `Finalizable`/`Upcastable` in `QuantLib/Internal/Type.hs` are used throughout. Think twice before one appears in a *public* signature as a constraint the user must satisfy: public APIs here favour concrete, dedicated types and functions over ad-hoc polymorphism, even at the cost of a few near-duplicate functions.
- **Choose collection types for semantics, ergonomics, and scale — not merely because upstream says `std::vector`.** Use ordinary lists for small collections that may validly be empty (especially optional/default schedules), `NonEmpty` when QuantLib requires at least one element or an empty value has no useful meaning, and storable `RealVector`/`RealMatrix` for large homogeneous numeric data such as paths, regression samples, and volatility grids. Keep small fixed-dimensional correlation/covariance inputs as boxed `Matrix` values when that is the more ergonomic API. The detailed binding checklist and marshaller choices live in `add-quantlib-method`.
- **Prefer collections of tuples to parallel public lists when elements correspond positionally.** If upstream accepts `dates` plus `values`, `strikes` plus `quotes`, or similar equal-length arrays, expose `[(Day, Double)]`, `NonEmpty (Double, GenQuote q)`, etc., and unzip only inside the binding. This makes mismatched lengths unrepresentable. Keep separate collections only when they are independent axes of a matrix/grid rather than pairwise records.
- **`GenForeignPtr`'s `_access`/`_mayFree` fields are a deliberate manual dictionary, not a missed abstraction.** An `Access a b` class would shrink `GenForeignPtr` to a coercible newtype, but c2hs emits an explicit type signature for **every** `{#fun#}`, so the constraint cannot be inferred in: **363 of 880** hooks take a polymorphic `` `GenX a' `` and would each need a hand-written context. c2hs's `CHSFun` type context is backtick-verbatim, and that form terminates on `'`, so a context mentioning `CQuote'` would need a prime-free constraint synonym per hierarchy level. It would also put a constraint in public signatures (against the rule above) and buys no correctness — `newCastForeignPtr` and `newGenForeignPtr` are already pinned by their result types.
- **`Period` has no dedicated type** — always marshalled as a plain `(Int, TimeUnit)`/`(Word, TimeUnit)` tuple via `fromEnumQuantity` (`addPeriod`, `forwardRateForPeriod`, `swaptionHelper`'s `maturity`/`length`/`fixedLegTenor`), with the C shim taking two plain `int`s and constructing `Period(len, (TimeUnit)unit)`. A bond price paired with its `Bond::Price::Type` is likewise a `(Double, BondPriceType)` tuple via `fromEnumDouble` (`Bond.yield`, `yieldFromPrice`, `zSpread`). `Money` is the same idea one type wider: a `(Double, Currency)` tuple whose second component is a foreign-pointer type rather than an enum, so it needs a `withX`-style continuation marshaller instead of a pure function — `withMoney :: (Double, Currency) -> ((CDouble, Ptr CCurrency) -> IO b) -> IO b` (`QuantLib/Internal/Type.hs`), used with c2hs's `&` splitter exactly like `withDoubleArray*`[Double]'&` (`exchange`, `convertToBaseCurrency` in `QuantLib/Currency.chs`). Reuse these tuple conventions rather than introducing wrapper types, and keep the convention symmetric: if a function's *output* is a `Money`-shaped tuple, its matching *input* parameter should be the same tuple, not two flattened arguments.
- **`std::variant<Real, Handle<Quote>>` (or `Rate`/`Spread`/`Volatility` in place of `Real`) collapses to a single `GenQuote`-taking function — never bind a second flat-`Double` overload.** A `simpleQuote` is a one-line existing binding (`QuantLib/Quote.chs`), so a caller with only a bare number can get the variant's `Real` alternative for free. Construct the variant alternative on the C++ side from a nullable `Quote*` (ternary idiom: `q ? variant<Real, Handle<Quote>>(*arg(q)) : variant<Real, Handle<Quote>>(Real(0.0))`, see `qlSofrFutureRateHelper`/`qlOISRateHelper` in `cbits/qlTermStructure.cpp`), not from two Haskell-visible functions. Confirmed via `sofrFutureRateHelper`, whose original dual-entry-point design was rejected for exactly this reason.

  Auditing this pattern has two traps. A same-name-sibling grep (`Double' -- ^rate/price/vol/spread/forward` alongside a same-name `GenQuote` function) only catches one `std::variant` function with two Haskell-visible entry points; it misses a plain-number constructor bound while a *separate*, differently-shaped Quote-taking overload sits unbound next to it. Crossing `tools/ql-methods-1.43.txt`'s status column against `Handle<Quote>` occurrences per class found that shape five times — `SabrInterpolatedSmileSection`, `Gsr`, `CounterpartyAdjSwapEngine`, `SwaptionVolatilityMatrix`, `HestonModelHelper` (its `s0` param) — all converted to their Quote overload, with the superseded plain-number tracking line flipped to `x` (permanently excluded) rather than inventing a new status letter. Second, the file's `v`/`u` marks are not reliable evidence of which overload is actually bound: for `FlatForward`, `BlackConstantVol`, `LocalConstantVol`, `ConstantCapFloorTermVolatility`, `ConstantOptionletVolatility`, `ConstantSwaptionVolatility`, `FlatHazardRate`, `CallableBondConstantVolatility`, `BachelierCapFloorEngine`, `BlackCapFloorEngine`, `BlackSwaptionEngine`, `BachelierSwaptionEngine` and `LocalVolSurface`, the plain-number sibling is marked `v` even though only the Quote overload has a real C shim. Check `cbits/*.cpp` directly rather than trusting the mark.
- **Wide constructors.** For the common case (a handful of trailing defaulted params), widen the existing narrow binding in place — every defaulted param becomes a required Haskell argument. Only past **10 trailing defaulted params** (`OISRateHelper`-scale) leave the narrow binding's signature untouched and add a *second*, full-arity entry point whose trailing params are bundled into a TH-generated options record (`deriveOptionsRecord` in `QuantLib.Internal.Syntax`), pre-populated with upstream's defaults via a generated `default<Name>` value. Worked example: `OISRateHelperOpts`/`oisRateHelperFull`/`oisRateHelperFull'` in `QuantLib/TermStructure/Yield.chs`; procedure and gotchas in the `add-quantlib-options-record` skill. (`AmortizingFloatingRateBond`'s 14-param options record and `AmortizingFixedRateBond`'s 8-param widen-in-place, both in `QuantLib/Instrument/Bond.chs`, are the pair this threshold was calibrated against.)
- **When a QuantLib abstraction requires subclassing/a callback and a straight per-call FFI callback would sit in a hot loop (per-MC-step, per-optimizer-component, per-grid-node), coarsen the language-boundary crossing rather than binding the callback as-is.** Two shapes, in order of preference:
  1. *Eliminate the callback*: find the algorithm's reusable inner primitive and expose that standalone, letting Haskell itself drive the outer loop. `lsmRegress`/`lsmRegressMulti` (`QuantLib/Method.chs`) are the worked example — instead of binding `LongstaffSchwartzPathPricer`'s per-path payoff callback, the per-exercise-date regression step is exposed on its own, called once per date across all paths, with Haskell walking the backward induction.
  2. *If no such decomposition exists*, keep a genuine callback but shape its signature to cross as infrequently as the algorithm allows — whole-vector/whole-grid per outer iteration, not per element. This is what QuantLib-SWIG does for `CostFunction`: its Python `PyCostFunction` (`SWIG/functions.i`) calls back into Python once per `value(Array x)` (the whole parameter vector), not once per component; its Java/C# FDM directors `FdmStepConditionDelegate`/`FdmLinearOpCompositeDelegate` (`SWIG/fdm.i`) likewise operate on the entire PDE grid `Array` per timestep, not per node.

  Don't assume shape 1 is always findable — QuantLib-SWIG's own `FdmInnerValueCalculatorDelegate` (`SWIG/fdm.i`) never found a batched alternative and stayed a genuine per-node, per-timestep director; some algorithms just don't decompose. And note the baseline QuantLib-SWIG falls back to when *no* coarsening is attempted at all: `Payoff`, `Exercise`, and `StochasticProcess` have no director in QuantLib-SWIG whatsoever, only fixed catalogues of concrete pre-implemented C++ subclasses — i.e. no customization offered, the most conservative fallback and not an instance of this trick.

  **`Payoff` and `StochasticProcess` were the two open cases here, and they resolved to opposite shapes — the lesson is that the answer comes from reading what the C++ actually does, not from the class's apparent similarity to one already solved.** `Payoff` is a shape-2 case with *no* coarsening available: its three pure virtuals include `operator()(Real price)`, and every consumer calls it one scalar at a time — `DiscretizedVanillaOption::applySpecificCondition` loops it node by node (`ql/pricingengines/vanilla/discretizedvanillaoption.cpp:71-77`), `FdmCellAveragingInnerValue` calls it inside a per-cell `SimpsonIntegral` (`fdminnervaluecalculator.cpp:81-106`), `AmericanPathPricer` per path per exercise index (`mcamericanengine.cpp:56`). Nothing upstream batches an `Array`, so `withCustomPayoff` accepts the per-price cost exactly as `withCustomFdmInnerValueCalculator` does. (`BasketPayoff::accumulate(const Array&)` is the one already-coarsened sibling — whole state vector per call — hence `withCustomBasketPayoff` alongside it.) `StochasticProcess`, by contrast, is a clean shape-1 case: `MultiPathGenerator` (what `pathGenerator` wraps) calls `process->evolve` once per timestep *per path*, but the reusable inner primitive is one level lower — the gaussian sequence generator it merely consumes — so `gaussianRsg`/`nextSequence` let Haskell write `evolve` itself with zero crossings per timestep, composing with `lsmRegress` into a full custom-SDE American MC (`test/example/QuantLib/Example/CustomSDE.hs`).

  Two facts that make this decomposition cheap rather than a compromise, both worth checking before reaching for a callback anywhere else: **a custom subclass would have had almost nowhere to go anyway** — every stock MC/FD/analytic engine's constructor is *compile-time* typed on a concrete process (`AnalyticEuropeanEngine` takes `shared_ptr<GeneralizedBlackScholesProcess>`), so the `dynamic_pointer_cast` sites understate the problem; and **`MultiPathGenerator` is the only fully process-generic consumer in the core**, which is precisely the one the sequence generator replaces.
- **A custom `Payoff` is rejected by most engines, and two of them *segfault* rather than throw — this must be in the haddock of anything that accepts one.** Three separate upstream mechanisms: (1) `dynamic_pointer_cast<StrikedTypePayoff>` + `QL_REQUIRE` (~136 sites — every `analytic*`, `binomial*`, `fd*` engine, and `MCEuropeanEngine`'s "non-plain payoff given"), a clean exception; (2) the *same cast with no check* in `FdBlackScholesVanillaEngine` (`fdblackscholesvanillaengine.cpp:155-162`) and `FdHestonVanillaEngine` (`fdhestonvanillaengine.cpp:119-132`), which then call `->strike()` on null — both are bound here, and no shim-side guard is possible; (3) `BlackCalculator::initialize`'s `p->accept(calc)` (`blackcalculator.cpp:149`), whose visitor knows only the four built-in striked payoffs, closing ~30 more engines via `Payoff::accept`'s own `QL_FAIL` default. The confirmed-generic consumers are `fdmLogInnerValue`/`fdmCellAveragingInnerValue` (hence `fdmSolve`) and `mcAmericanEngine` with `controlVariate = False` — its `lsmPathPricer` passes the payoff through uncast, and the only `StrikedTypePayoff` cast on that path is a soft scaling tweak that is silently skipped (`mcamericanengine.cpp:47-52`).

  **Category (2) is fixable, and the fix is to satisfy the cast rather than guard against it — read *what the downcast is for* before writing a case off as unusable.** `FdBlackScholesVanillaEngine` wants `strike()` for exactly two things, both mesher geometry (grid extent, and the node-concentration point), and then hands the payoff to `FdmLogInnerValue`, which takes a plain `Payoff` — so the engine's *pricing* was never payoff-specific, only its grid sizing was. `StrikedTypePayoff` adds no pure virtuals over `Payoff` (it supplies `description()`, `TypePayoff` supplies `optionType()`), so `HsStrikedPayoff : public StrikedTypePayoff` carrying an advisory `(type, strike)` is a few lines, and `withCustomStrikedPayoff` then prices an arbitrary Haskell payoff *correctly* through both FD vanilla engines instead of segfaulting. The `(type, strike)` pair is advisory — it steers the grid, it does not define the payoff — which is worth saying plainly in the haddock so callers don't think it constrains the function. Category (1) and (3) stay closed, correctly: there is no closed-form price for an arbitrary function, so a clean `QL_FAIL` is the right answer there.
- **A Haskell callback stored inside a C++ object needs its `FunPtr` bracket to span the whole *use*, not the construction call — which is why a custom `Payoff` is a `Payoff` ADT constructor holding a `FunPtr`, not a `withX`-style marshaller.** Every `Payoff` consumer stores the `shared_ptr<Payoff>` and calls back into it later (an `Instrument` at `NPV` time, an `FdmInnerValueCalculator` at `fdmSolve` time), so a `{#fun#}`-argument-position marshaller would free the `FunPtr` the instant the constructor returned. `withCustomPayoff`/`withCustomBasketPayoff` therefore hand the caller a `Payoff`/`BasketPayoff` *value* valid only inside the continuation — same rule, same reason, as `withCustomFdmInnerValueCalculator`'s raw-import bracket. The payoff ADT keeps working unchanged for every existing consumer, since they all already take the ADT.
- **Scale a numeric test tolerance to the magnitude of the value** (~1e-6 relative); don't pin it at 1e-6 absolute. Bootstrapped curve results and optimiser-calibrated model parameters differ in the last few places between platforms — aarch64/macOS and the x86_64 container disagree at ~1e-4 on the CDS survival probabilities and the G2 calibrated parameters — so an absolute 1e-6 on a value of magnitude 1e4 isn't a stricter test, just one that fails the lts-18.8 gate. Recording a value at more digits and tightening its tolerance are separate decisions.
- For a new `test/example/QuantLib/Example/*.hs` port, check `~/Src/QuantLib/test-suite/*.cpp` first: an upstream test on the same class/scenario often has real, already-cached expected values (e.g. `inflationcpibond.cpp`'s `testCleanPrice` gives exact `dirtyPrice`/`cleanPrice` for a `CPIBond`), stronger and cheaper than hand-deriving. Match the upstream fixture (index, calendar, schedule, quotes) closely enough that the cached numbers apply. Fall back to a self-consistency check ("reprices to its own fair rate") only after grepping for the class's constructor across `test-suite/*.cpp` and finding nothing.
  - A grep hit isn't automatically usable: check whether the upstream test's *fixture* is buildable from hasquant's current bindings before promising a golden-value comparison, not just whether the class under test is bound. Binding `gaussian1dCapFloorEngine` found a real cross-check at `test-suite/markovfunctional.cpp:1234` (`Gaussian1dCapFloorEngine` vs `BlackCapFloorEngine`, 1bp tolerance) — but it only exercises a `MarkovFunctional` built via its caplet-smile-matching constructor (`iborIndex`/`capletExpiries`/`capletVts`), and hasquant binds only `MarkovFunctional`'s other constructor (swaption/CMS-calibrating, used for the Gaussian1d bermudan-swaption examples). Nothing was erased by upstream here (contrast the `NonstandardSwaption::calibrationBasket` case above) — the reference fixture simply isn't constructible yet, which only shows up by reading past the grep hit to what it actually builds, not by trusting that the class name matched.
- **A Monte Carlo example built on `pathGenerator`/`sobolPathGenerator` needs a fixed nonzero seed before its output can be pinned in a test.** `MersenneTwisterUniformRng` treats seed `0` as "seed from entropy" (`ql/math/randomnumbers/mt19937uniformrng.hpp`), so `seed = 0` (as `test/example/QuantLib/Example/TARF.hs` had) makes every run's paths, and hence its NPV, genuinely different. With a fixed nonzero seed MT19937's integer draw sequence is identical across platforms, so only the FP transform/evolution differs, at the usual ~1e-4–1e-6 relative level.
- **Add a martingale-style self-consistency check alongside any FX/equity process example.** In TARF, comparing the simulated path mean (`simFwds`) against the deterministic discount-curve-implied forward (`implFwds`) — which must match under the risk-neutral measure — showed a persistent one-directional ~1% gap, not MC noise (MC error at that trial count is ~0.04%). The cause was `garmanKohlagenProcess`'s foreign/domestic `YieldTermStructure` arguments passed in the wrong order (ILS as foreign, EUR as domestic, for a spot quoted ILS-per-EUR — EUR is the foreign currency there), flipping the sign of part of the drift.
- **`QuantLib.Time.Calendar.advance` with a `Days`-unit period is not plain date arithmetic — don't use it to replicate an upstream fixture's `Date + Period(n, Days)`.** `Calendar::advance` (`ql/time/calendar.cpp`) special-cases `unit == Days`: it steps one *business day* at a time, `n` times, skipping weekends/holidays regardless of the given `BusinessDayConvention` — unlike `Weeks`/`Months`/`Years`, which do plain `d + n*unit` then apply the convention as an adjustment. Porting a fixture that computes dates via raw `Date + Period(years,Years) + Period(days,Days)` (e.g. `test-suite/inflationvolatility.cpp`'s EUR curve node dates) by calling `advance` for both parts silently reorders nodes once enough holidays/weekends separate two residual-day offsets — caught here as a downstream `InterpolatedCurve` "dates not sorted" exception with the two flagged dates months apart, not a same-fixture off-by-one. Fix: since a hasquant `Day` is a plain `Data.Time.Calendar.Day`, do the years step with `addGregorianYearsClip` and the residual days with `addDays` directly, bypassing `advance` entirely for this pattern.
- **A golden-value test needing a specific year fraction must derive its exercise/query date and the year fraction from the *same* source, never compute them independently.** `DayCounter::yearFraction` is bound, as `QuantLib.Time.Schedule.years :: DayCounter -> Day -> Day -> Maybe Day -> Maybe Day -> IO Double` (named after the upstream method's return type, not its own name — grep missed it once for exactly that reason, so check `Schedule.chs` before assuming it's absent). Given an upstream fixture's own date (e.g. `settlementDate + 6*Months`, via `QuantLib.Time.Date.addPeriod`), call `years` on that same date to get the exact year fraction for any formula that needs one, rather than hand-picking a literal (e.g. `0.5`) and separately rounding it into a date via `addDays (round (t * basis)) evalDate` — the rounded date and the literal silently diverge (`round(0.5 * 365)` is `182` or `183`, not exactly `0.5 * 365`), enough to blow a tight (`2e-7`-scale) closed-form tolerance while looking like noise. See `QuantLib.Spec.Process`'s Heston/Bates-vs-Black tests for the worked pattern. `addDays (round (t * basis))` is still the right tool when the *date itself* is the fixture's primitive (e.g. upstream states the offset in literal days, or 360-day fixing-schedule spacing) and no independent year-fraction formula reads `t` back — that's not this trap.
- **When a QuantLib golden-value fixture disagrees with your binding, don't assume the binding is wrong — reproduce the fixture in raw C++ against the same installed `libQuantLib` first.** Porting `test-suite/inflationvolatility.cpp`'s `testYoYPriceSurfaceToVol`, every stripped vol came out ~4–6% high relative to the cached `volATyear1`/`volATyear3` arrays, uniformly across all 11 strikes and both maturities (a systematic bias, not noise) — while the ATM-swap-curve half of the same fixture (`testYoYPriceSurfaceToATM`) matched upstream's cached values to 2e-5. A ~15-line standalone `.cpp` (no boost, no hasquant, just the upstream test's own `setup()`/`setupPriceSurface()`/`testYoYPriceSurfaceToVol` bodies verbatim) compiled and linked against `/opt/homebrew/Cellar/quantlib/1.43` reproduced the *same* "high" values hasquant did, not upstream's cached ones — proving the discrepancy is a real behavior change in QuantLib since the fixture's cached numbers were recorded (2009), not a hasquant bug. Both `KInterpolatedYoYOptionletVolatilitySurface` and `InterpolatedYoYOptionletStripper` carry their own upstream doc comment saying as much: `\bug Tests currently fail`. Pin the test to the value both independent implementations agree on, with a comment explaining why it isn't upstream's own cached number, rather than either trusting a stale fixture or chasing a nonexistent binding bug.

## c2hs and the C shim

See the `c2hs-shim-patterns` skill for `{#pointer#}` pragma rules, C shim marshalling patterns (`alloca-`/`preArray`), `Handle<YieldTermStructure>` semantics, multiple-inheritance/upcast shims, cross-module enum-import avoidance, and `GenX` mnemonic naming.

- **`cbits/*Aux.cpp` exist to hold every "runtime enum int selects a template argument" dispatch, and each axis gets exactly one generic-lambda dispatcher** — `dispatchInterpolation`/`dispatchInterpolation2D`/`dispatchDefaultTrait` in `qlTermStructureAux.cpp`, `dispatchTree`/`dispatchRng`/`dispatchStat`/`dispatchRngStat` in `qlPricingEngineAux.cpp`. Each caller spells its `new SomeTemplate<...>(args)` once, in a lambda; the ~2000 lines of hand-duplicated `switch(interpolator){switch(approximator){...}}` / per-engine `template <class RNG> ...AuxStat` helpers these replaced are not to come back. Prefer the Aux TU for anything instantiating a template per enum value even when the class is bound elsewhere (`qlCPICapFloorTermPriceSurfaceAux`, `qlKInterpolatedYoYOptionletVolatilitySurfaceAux` and the `qlSetBlackVariance*InterpolationAux` setters moved out of `qlTermStructure.cpp` on that rule); the limit is whether the helper can present a non-template signature at the TU boundary. **A dispatcher takes its result type as an explicit leading template argument and must never deduce it with a trailing `-> decltype(make(...))`** — that probe is an unevaluated operand, so clang emits the constructed class's constructor but not its vtable, and the missing destructor only surfaces when GHC dlopens the dylib, for the one type the probe named. Compiling clean is not evidence; diff the object's unresolved-symbol closure against `git show HEAD:`'s. Details and the two standing exceptions (LogCubic under the YoY optionlet stripper; anything that must exclude an arm) are in the `c2hs-shim-patterns` skill.
  - **The rule keys on "selects a *template argument*", not on "an enum picks behaviour" — a catalogue that fits inside one instantiation stays where the class is bound.** `DerivedQuote`/`CompositeQuote`/`MultiCompositeQuote` are templates over a functor, so a `QuoteOp` catalogue looks like an Aux case; it isn't. A single `DerivedQuote<QuoteUnaryOp>` over a functor struct that switches on the op *inside* `operator()` covers all four ops, so there is no per-enum-value instantiation to dispatch and the shims stay in `qlMisc.cpp` next to the other quotes. Reach for an Aux dispatcher only when the enum value must appear in the template argument list.
- **`trackAllocations` tracing is switched on or off in exactly one place, and that place is a template.** `cbits/qlaux.h` holds the single `#ifdef QLTRACK_ALLOCATIONS` (the `ObjClassName` label table, `traceStream()`, `emit()`, `inline constexpr bool trackAllocations`); every verb — `arg`/`alloc`/`allocShared`/`ret`/`del`/`delArray`/`delWith`/`retPtrArray`/`allocAs` — routes through `traceAs<Label>(what, p)`, whose body, *including the null test*, sits inside `if constexpr (trackAllocations)`. Discarded branches are only left uninstantiated inside a template, so a non-template shim (`qlFreeInts`, a `qlFree*` in some `.cpp`) must never host the `if constexpr` itself — it would still be fully type-checked with the flag off, which is the whole thing this arrangement buys. Add a new verb next to the others rather than a new `#ifdef` at a call site; an `if (p)` in a free function now signals a *semantic* null check (the callee isn't null-safe, as in `delWith`), never a tracing one. Only two things in a `.cpp` may still name the flag: `traceStream()`'s definition in `qlMisc.cpp`, and a `QL_TRACE_NAME` block for a type that cannot be named from `qlaux.h`. Details and the audit checklist live in the `audit-allocations` skill.
- **Factory-table `make*` templates return the base pointer, never a concrete pointer or `auto`.** `alloc()` labels objects by static type, so concrete returns disagree with the base-type finalizer and corrupt allocation traces. Keep each table's function-pointer alias at the base type: it makes a wrong return type fail to compile. Templates stay outside `extern "C"`; exceptional constructors use a lambda with the same base-pointer type.
- **Avoid raw `foreign import ccall` declarations in binding `.chs` files** — prefer `QuantLib.Internal`/`QuantLib.Internal.Type`/`QuantLib.Internal.Common`, mirroring where their own low-level FFI plumbing (`qlFreeAdditionalResults`, `peekStructArray`, `GenForeignPtr`, ...) already lives. A single, contained, occasional raw call local to one binding module is fine; don't reach for it as a default just because a `{#fun#}` won't fit — that's the shape of problem `Internal`/`Internal.Type`/`Internal.Common` already exist to hold, and scattering raw FFI declarations across binding modules is how a marshaller like `RawResult`/`AdditionalResultVal` ends up hand-rolled in `QuantLib.Instrument` (pulling in five unrelated `Foreign.*` imports) instead of centralized where other cross-cutting marshalling lives.

## Template Haskell (`QuantLib/Internal/Syntax.hs`)

- **Verify any refactor of the `derive*` functions with a `-ddump-splices` diff, not by reading.** Capture the dump before and after, normalise it (strip the `file:line:col` prefixes, collapse TH's `x_a1n2U` unique suffixes to a placeholder), and require the two to be **byte-identical**; that is what pins the things nothing else can see — notably per-field strictness (`Bang NoSourceUnpackedness SourceStrict` for the enum ADTs' `!` fields vs `NoSourceStrictness` for the options records' lazy ones), which no `test/smoke/` script or test can catch because they check values, not strictness. Getting the dump out has its own trap: **neither `touch` nor `stack build --force-dirty` re-triggers it** on an otherwise up-to-date build, because `-ddump-splices` doesn't change the ABI and GHC's recompilation avoidance skips the module — delete the splice modules' `.hi`/`.o` under `.stack-work/dist/*/build/` first, then build with `--ghc-options=-ddump-splices`.
- **The module builds its output as raw `Dec`/`Con`/`Exp`/`Pat` constructors, not quotation brackets or `TH.Lib` combinators** — with two forced exceptions, because `template-haskell` changed their arity *inside* the supported GHC range (8.10's 2.16 through 9.10's 2.22), so a literal application fails at one end or the other: `ConP` gained a `[Type]` field for visible type application in 2.18 (wrapped as the local `conPat`), and `TyVarBndr` gained a flag parameter in 2.17, so `PlainTV` took a second argument (hence `plainTV` surviving in `deriveOptionsRecord`). `TupE` is *not* such a case — it has taken `[Maybe Exp]` since 2.16, across the whole range. Check any newly used TH constructor against both ends before writing it raw; the lts-18.8 gate is the only thing that catches this.
- **`mkName` for generated top-level names is deliberate, not a hygiene bug.** The merged ADTs, mapper/ordinal/tenor functions, options record and its `default<Name>` value are exactly what the splice site then refers to by hand, so `newName` would make them unreferenceable. `newName` belongs only on pattern variables inside generated clauses.
- **Pass a spec record, not positional arguments.** `CrossEnumSpec` and `IborConstructorSpec` prevent interchangeable `String`/`Name` arguments from being transposed silently. Use the same shape for new `derive*` entry points.
- **A top-level splice can only see `{#fun#}`-generated names that come *after* it in the file — never mid-file, regardless of textual position relative to the specific pragma.** c2hs appends every `{#fun#}`-generated `foreign import ..._'_` stub at the *physical end* of the file it preprocesses, no matter where the `{#fun#}` pragma establishing it sits. A top-level TH splice forces GHC to split the module into declaration groups at that point, so any `{#fun#}` wrapper function textually before the splice loses sight of its own stub (still to come, in the final group): adding `$(deriveReadInstance ...)` anywhere in `QuantLib/Time/Calendar.chs` — even at the very end, after `calendar`'s own definition — broke every `{#fun#}` wrapper in the file with "Variable not in scope: qlJointCalendar2'_" and similarly-misattributed errors (GHC's error pointed at the wrong nearby function's line, since the two groups' positions no longer lined up with what the reader expects). A splice is only safe in a `.chs` file if it comes before *every* `{#fun#}` pragma in that file (`deriveCrossEnum`/`deriveIborConstructor`'s own splices already satisfy this) or the file has no `{#fun#}` pragmas at all (`QuantLib/Internal/CalendarEnum.chs`). `deriveReadPlain`/`deriveReadInstance` in `Syntax.hs` are the worked example of designing around this: generate only what's safe to generate at the type's declaration site, and hand-write (or splice from a genuinely different, cycle-free module) whatever needs a same-file `{#fun#}` wrapper.

## Documentation upkeep

- `QuantLib/Internal/Type.hs` carries a haddock ASCII tree directly above **every** hierarchy root's `type Xxx = GenXxx CXxx`/`newtype GenXxx a` declaration (`CalibratedModel`, `TermStructure`, `Instrument`, …), listing every member indented by parent/child. The notation is defined once, in the legend under `-- TYPE HIERARCHIES` in that file: `X*` = abstract *here* (hasquant binds no constructor returning an X), `X + Y` = X also reaches secondary interface Y, `X (CFoo')` = X's C type where it isn't the expected `C<X>'` (only `OvernightIborIndex` today). Update the relevant tree whenever you add a type to any hierarchy — it's the only place each hierarchy's full shape is written down, and it rots silently. Payoff/Exercise are documented in their own files, not here. `X*` is not derivable from upstream: `Option` and `Swap` are concrete C++ classes yet unconstructible here, while `Quote`/`Index`/`TermStructure` are pure-virtual upstream yet routinely returned by bindings — so mark it by hand, and don't read an unmarked node as a claim of the opposite.
- `tools/ql-methods-1.43.txt` (the current version's tracking dump): set the affected lines to `v`/`u` as soon as you add a method/class binding — see the `add-quantlib-method` skill for the status vocabulary. Don't let it drift and rely on a bulk resync later.
  - The dump has confirmed false positives in both directions, so a coverage audit must cross-check `cbits/*.h` directly rather than trust it. Header-level "zero bound methods" summaries have wrongly flagged classes that are in fact bound (`CompositeInstrument`, `CliquetOption`, `HimalayaOption`, `PagodaOption`, `MCEuropeanEngine`, `MCBarrierEngine`, the MC Asian engines, `MCDigitalEngine`, `IntegralCdsEngine`, `AnalyticDividendEuropeanEngine`, `ImpliedVolatilityHelper`, `OvernightIndexFuture`, `MultipleResetsSwap`) because the per-method lines don't line up with actual shim names; conversely, some genuinely-bound lines sit stale at `?` (e.g. `CalibratedModel::params()`) because nothing flipped them at binding time.
  - Several `ql/experimental/` headers in QuantLib 1.43 are upstream deprecation stubs — license text plus a `#pragma message("... this file is empty and will disappear ...")` and nothing else (`ql/experimental/averageois/*`, `ql/experimental/risk/sensitivityanalysis.hpp`, `ql/experimental/risk/creditriskplus.hpp`; `ql/experimental/fx/*` is a forwarding stub to already-bound `ql/quotes/deltavolquote.hpp` and `ql/pricingengines/blackdeltacalculator.hpp`). `wc -c` under ~1200 bytes plus `grep 'will disappear'` catches them. Zero tracking-dump lines for such a header means the class no longer exists upstream, not a missed binding — don't chase it.
- README.md's Roadmap (under `# Goals and Scope`): when finishing a feature, remove any item it resolves.
- `test/main/QuantLib/MainTest.hs` is a thin dispatcher (`hspec $ do X.spec; Y.spec; ...`), not a 1400-line `do` block: each topic's `describe` blocks live in their own `QuantLib.Spec.*` module under `test/hspec/QuantLib/Spec/`, grouped by what they test (dates/schedule, calendars, currency/day-counter, interest-rate/cash-flow, term-structure, the `*Example` blocks, …), with shared arbitrary instances and comparison helpers (`listClose`, `closePrec`, `ValidDay`, …) in `QuantLib.Spec.Helpers`. Add new `describe` blocks to the module matching their topic; don't grow `MainTest.hs` itself back into one file.
