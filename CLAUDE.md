# hasquant

Haskell bindings to QuantLib via c2hs, with a C++ shim layer in `cbits/`.

## Before inventing a workaround

This codebase has accumulated many special-case patterns for recurring problems (c2hs cross-module enum-import cycles, multi-inheritance secondary interfaces, wide-arity constructors). Before adding a hand-rolled type mirroring a C enum, a new module, or a new abstraction layer, grep this file, the codebase, and `.claude/skills/` for how a similarly-shaped problem was already solved. A plausible-looking one-off fix is usually a rediscovery, and diverging from the established pattern drops the safety properties that pattern already has: `CPIInterpolationType` was first hand-rolled outside `QuantLib.Internal.Enum` — the existing home for cross-cutting enums like `TimeUnit`, which live there to avoid cyclic deps — then moved back into it.

## Build and test

- `make` — C++-only compile check; fast, no Haskell rebuild.
- `stack build --test --no-haddock` — full build and test suite.
- `stack test --ta '--skip LONG'` — fast path (0.8s vs 21s). Slow tests are marked by suffixing `(LONG)` to the `it`/`describe` description. The effective threshold is ~2.5s, not tens of seconds: measure before labelling, and re-check existing labels (the equity option block was labelled `(LONG)` while running in 0.5s).
- **GHC 8.10 gate.** The package supports GHC 8.10.6 / base 4.14.3.0, which is also its declared floor (`base >=4.14`, set in `package.yaml` — `hasquant.cabal` is hpack-generated, so edit the former and let `stack build` regenerate the latter), verified via the lts-18.8 Docker image. Nothing merges until this passes:
  `docker compose run --rm hasquant sh -c 'stack build --resolver lts-18.8 --flag hasquant:buildExample --no-haddock && stack --resolver lts-18.8 test'`
  (no `-it`, which fails without a TTY). It catches two things the local GHC 9.10 build cannot: post-8.10 `base` functions creeping in — often *via* an hlint suggestion, e.g. `Data.Functor.unzip` (base 4.19+) — and types 9.10 infers but 8.10 rejects (a `let`-bound helper containing a list literal under `OverloadedLists` over-generalised to an `IsList`-polymorphic type and failed with `Illegal equational constraint`; fix: give the helper an explicit signature).
- After testing: no new compilation warnings, and a clean `hlint` run. Check a hint actually holds before applying it — two here turned out wrong. `Avoid NonEmpty.unzip` fires on the bare name `unzip` in *any* module importing `Data.List.NonEmpty`, with no type resolution at all: it flags plain `Prelude.unzip` over ordinary lists, and importing `Data.Functor.unzip` explicitly doesn't silence it. For a genuinely wrong hint, add a targeted `- ignore: {name: ..., within: Module}` to `.hlint.yaml` with the evidence in a comment rather than contorting the code — the goal is a clean run so real hints stay visible.

### Stale builds, and keeping `smoke/` current

Editing a C header (e.g. `cbits/qlEnumObjects.h`) without touching any `.chs` file leaves `cabal build`/`stack build` silently stale: neither tracks that a `.chs` file's `#include`d header changed, so the build reports success without re-running c2hs, and tests then pass against the *old* generated code. Do a clean build if in doubt. A compiled build is not proof that generated enum cases actually changed — `smoke/` holds standalone end-to-end value-level checks for that, run via `cabal exec -- ghc -package hasquant smoke/Foo.hs -o /tmp/foo && /tmp/foo`.

The same class of problem hits the lts-18.8 Docker gate across sessions, for a different reason: `compose.yaml` persists `stack-root`/`ghcup-root`/`hasquant-work` as named volumes so rebuilds are fast, but that means a container run can silently reuse a stale build from an earlier session instead of reflecting current sources — no error, just wrong numbers. This produced a false "24% platform divergence" in a CDS example test (see `git log` for the fix) that a `stack --resolver lts-18.8 clean hasquant` before rebuilding made disappear entirely (the container then matched macOS to ~1e-10 relative). If a gate result looks structurally wrong rather than numerically noisy — especially a large, round-looking discrepancy on only some fields — clean before trusting it.

So: whenever you add an enum-dispatched case (a new currency, calendar, or index variant — see the `reconcile-*`/`add-quantlib-index` skills), add or extend a `smoke/` script that constructs the new case and prints something derived from it, and actually run it. This is what catches the staleness above and any enum/factory-table order mismatch; `test/` won't, since it doesn't know about cases it was never written to check.

### Test values and tolerances

- Scale a numeric tolerance to the magnitude of the value (~1e-6 relative); don't pin it at 1e-6 absolute. Bootstrapped curve results and optimiser-calibrated model parameters differ in the last few places between platforms — aarch64/macOS and the x86_64 container disagree at ~1e-4 on the CDS survival probabilities and the G2 calibrated parameters — so an absolute 1e-6 on a value of magnitude 1e4 isn't a stricter test, just one that fails the lts-18.8 gate. Recording a value at more digits and tightening its tolerance are separate decisions.
- For a new `test/QuantLib/Example/*.hs` port, check `~/Src/QuantLib/test-suite/*.cpp` first: an upstream test on the same class/scenario often has real, already-cached expected values (e.g. `inflationcpibond.cpp`'s `testCleanPrice` gives exact `dirtyPrice`/`cleanPrice` for a `CPIBond`), stronger and cheaper than hand-deriving. Match the upstream fixture (index, calendar, schedule, quotes) closely enough that the cached numbers actually apply. Fall back to a self-consistency check ("reprices to its own fair rate") only after grepping for the class's constructor across `test-suite/*.cpp` and finding nothing.

## API design

- **Don't mirror QuantLib's C++ hierarchy 1:1.** A bound class with no calculations of its own, never needed as an argument type elsewhere, doesn't need a Haskell object/pointer type — a constructing function returning the parent (or grandparent) is enough. That's already how pricing engines work: `discountingSwapEngine`, `blackCapFloorEngine` etc. all return the generic `PricingEngine`. Introduce a dedicated type only when the class has its own calc/getter (`FxForward`'s `fairForwardRate`, `ForwardRateAgreement`'s `forwardRate`) or must be passed around as its own type. Same idea one level down: don't bind a constructor for a class whose constructors only delegate to a more complex one with no logic of their own (QuantLib's `FixedVsFixedSwap`-style thin convenience subclasses) — bind straight through to what it actually constructs.
- **Module placement follows the topical family, not C++ inheritance.** `FxForward` lives in `QuantLib/Instrument/Forward.chs` alongside `ForwardRateAgreement`/`BondForward`, though it isn't a C++ `Forward` subclass. Leave the generic root module (e.g. `QuantLib/Instrument.chs`) for hierarchy-wide methods.
- **Bind few inspectors** — only what scheduling/pricing/output needs. `Schedule` binds `dates` out of ~20 upstream inspectors, `Calendar` binds none of its 4 (`empty()`/`name()`/`addedHolidays()`/`removedHolidays()`), `Currency` a curated 5 of 10. Prefer one targeted getter (as with `FxForward`'s `fairForwardRate`/`npvSourceCurrency`/`npvTargetCurrency`) over binding everything the C++ class exposes.
- **Setters** exist only for engine/pricer wiring (`setPricingEngine`, `setCouponPricer(s)`), the global `Settings` singleton, and `SimpleQuote.setValue` (mutable by design) — not as general field mutators. Prefer constructing a new object over mutating one (bake a flag into a constructor rather than adding a post-construction setter). **Confirm with the user before adding any new setter/mutator**, even mid-exploration — don't rely on self-judging it against this rule.
- **Typeclasses** are fine, even normal, as *internal* plumbing — `Finalizable`/`Upcastable` in `QuantLib/Internal/Type.hs` are used throughout. Think twice before one appears in a *public* signature as a constraint the user must satisfy: public APIs here favour concrete, dedicated types and functions over ad-hoc polymorphism, even at the cost of a few near-duplicate functions.
- **`Period` has no dedicated type** — always marshalled as a plain `(Int, TimeUnit)`/`(Word, TimeUnit)` tuple via `fromEnumQuantity` (`addPeriod`, `forwardRateForPeriod`, `swaptionHelper`'s `maturity`/`length`/`fixedLegTenor`), with the C shim taking two plain `int`s and constructing `Period(len, (TimeUnit)unit)`. A bond price paired with its `Bond::Price::Type` is likewise a `(Double, BondPriceType)` tuple via `fromEnumDouble` (`Bond.yield`, `yieldFromPrice`, `zSpread`). Reuse these tuple conventions rather than introducing wrapper types.
- **Multiple inheritance where the second base is an interface needed by one consumer** (`AffineModel`, needed only by `analyticCapFloorEngine`; `Gaussian1dModel`, only by `Gaussian1dSwaptionEngine`): don't add a second `Upcastable` node — `Upcastable` is single-parent (one `Base` per type), so a second real base has nowhere to go. Mirror the `AffineModel` pattern in `Internal/Type.hs` (search `CAffineModel'`): keep the leaf's one `Upcastable` instance pointed at its true hierarchy parent, and separately add a standalone (non-`Upcastable`) `qlXAsInterfaceY :: Ptr CX' -> IO (Ptr CInterfaceY')` shim per leaf, a hand-written nested ADT (`data InterfaceY = X X | Z Z`), and a `withInterfaceY` that pattern-matches and calls `withUpcast qlXAsInterfaceY f` per case. The consuming engine takes the concrete ADT directly (`` withAffineModel*`AffineModel' ``), not a polymorphic `GenXxx m`. ADT adaptors are for passing an object as an argument; common/overloaded methods are mostly modelled as type classes instead (`HasImpliedVol`, `HasQuanto`).
- **Wide constructors.** For the common case (a handful of trailing defaulted params), widen the existing narrow binding in place — every defaulted param becomes a required Haskell argument. Only for a genuinely long list (`OISRateHelper`-scale, ~19+) leave the narrow binding's signature untouched and add a *second*, full-arity entry point whose trailing params are bundled into a TH-generated options record (`deriveOptionsRecord` in `QuantLib.Internal.Syntax`), pre-populated with upstream's defaults via a generated `default<Name>` value. Worked example: `OISRateHelperOpts`/`oisRateHelperFull`/`oisRateHelperFull'` in `QuantLib/TermStructure/Yield.chs`; procedure and gotchas in the `add-quantlib-options-record` skill.

## c2hs and the C shim

- **`{#pointer#}` flags decide what a bare-backtick `{#fun#}` return spec (`` ->`T' ``, no named out-marshaller) produces.** The wrong combination compiles-then-crashes or fails type-checking confusingly rather than erroring at the pragma:
  - `{#pointer *T foreign finalizer F newtype#}` (c2hs owns the type) generates a `ForeignPtr`-wrapped newtype `T` with finalizer `F`; a bare `` ->`T' `` auto-wraps the raw returned pointer into `T`.
  - `{#pointer *T foreign -> X nocode#}` (used when `T`'s `Finalizable`/`Upcastable` instances are hand-written in `QuantLib/Internal/Type.hs` — the pattern for every class hierarchy: Option, Quote, Bond, Payoff/Exercise, …) says `T` is a `ForeignPtr`-managed value shaped like `X` but suppresses the wrapper. A bare `` ->`T' `` still tries to auto-wrap into a `ForeignPtr`, which fails (`Couldn't match type 'ForeignPtr X' with '...'`) unless `T` really is that shape.
  - `{#pointer *T nocode#}` (no `foreign`, no `-> X`) is what you want for a genuinely raw `Ptr T` (e.g. to hand off for hand-written `Upcastable` upcasting). A bare `` ->`T' `` here marshals `T` *by value* and GHC rejects it (`T cannot be marshalled in a foreign call`). c2hs has no built-in passthrough out-marshaller, so write and name one: `peekPtr :: Ptr a -> IO (Ptr a); peekPtr = pure`, then `` ->`T'peekPtr* ``.
- **Every `Ql*AsY` upcast shim in `cbits/` is `ret(new QlY(*arg(o)))`** — a fresh, independently-owned handle sharing the underlying QuantLib object via `shared_ptr` refcounting, not a non-owning pointer reinterpretation. This is exactly the ownership pattern `Upcastable`/`AnyOf`/`freeUpcast` assume (free the upcast intermediate immediately after the consuming call returns); reuse it for a new hierarchy edge without re-deriving it.
- **Don't move `QuantLib.Internal.*` from `other-modules` to `exposed-modules`** to work around a c2hs cross-module `{#import#}` ordering problem. It only affects **enum** types referenced inside a `{#fun#}` in another module, since `{#import M#}(Type)` needs `M`'s `.chi` file to already exist, and `other-modules` isn't part of the ordered-by-list-position scheme `exposed-modules` uses (reordering, even fully serial `-j1` builds, doesn't fix it). Avoid the problem instead: add dedicated constructors that hardcode the enum value inside their own C++ shim (`ActualActualBond' :: Schedule -> DayCounterConstructor`, see the `reconcile-daycounters` skill), so no enum crosses a module boundary. If a parameterized enum genuinely must cross (rare), marshal it as a plain `Int`/`CInt` in the low-level, unexported `{#fun#}` glue only, converting via `fromEnum` at its one call site — the public constructor stays fully typed. Pointer/foreign types (like `Schedule`) never hit this: just re-declare a local `{#pointer#}` in the file that needs it, as `Schedule` already is in several `.chs` files.
- **Don't export c2hs's raw double-underscore enum constructors** (`ActualActual__Bond`, from `add prefix = "ActualActual__"`) through any public module — they read as generated, not like the rest of the API. Give a user-facing case a proper dedicated constructor instead of exporting the enum type.
- **Mirror upstream's explicit enum values when it skips a deprecated leading case.** `CPI::InterpolationType` is `AsIndex = 0, Flat = 1, Linear = 2`, so the `cbits/qlEnumObjects.h` enum must say `CPIFlat = 1, CPILinear = 2` rather than renumbering from 0 — renumbering silently aliases each hasquant case to upstream's *next lower* one, and the C++ cast is unchecked so it builds and passes with no warning. This shipped undetected for a full session. Guard any such enum with a `smoke/` check that constructs both cases from identical inputs and asserts the outputs differ (see `smoke/CheckInflation.hs`'s Flat-vs-Linear NPV check) — a comment doesn't catch it. Keep the fix on the C/C++ side (the header's values, plus the one hand-written Haskell marshaller if one already exists), don't add a Haskell-side abstraction for it.

## Template Haskell (`QuantLib/Internal/Syntax.hs`)

- **Verify any refactor of the `derive*` functions with a `-ddump-splices` diff, not by reading.** Capture the dump before and after, normalise it (strip the `file:line:col` prefixes, collapse TH's `x_a1n2U` unique suffixes to a placeholder), and require the two to be **byte-identical**; that is what pins the things nothing else can see — notably per-field strictness (`Bang NoSourceUnpackedness SourceStrict` for the enum ADTs' `!` fields vs `NoSourceStrictness` for the options records' lazy ones), which no `smoke/` script or test can catch because they check values, not strictness. Getting the dump out has its own trap: **neither `touch` nor `stack build --force-dirty` re-triggers it** on an otherwise up-to-date build, because `-ddump-splices` doesn't change the ABI and GHC's recompilation avoidance skips the module — delete the splice modules' `.hi`/`.o` under `.stack-work/dist/*/build/` first, then build with `--ghc-options=-ddump-splices`.
- **The module builds its output as raw `Dec`/`Con`/`Exp`/`Pat` constructors, not quotation brackets or `TH.Lib` combinators** — with two forced exceptions, because `template-haskell` changed their arity *inside* the supported GHC range (8.10's 2.16 through 9.10's 2.22), so a literal application fails at one end or the other: `ConP` gained a `[Type]` field for visible type application in 2.18 (wrapped as the local `conPat`), and `TyVarBndr` gained a flag parameter in 2.17, so `PlainTV` took a second argument (hence `plainTV` surviving in `deriveOptionsRecord`). `TupE` is *not* such a case — it has taken `[Maybe Exp]` since 2.16, across the whole range. Check any newly used TH constructor against both ends before writing it raw; the lts-18.8 gate is the only thing that catches this.
- **`mkName` for generated top-level names is deliberate, not a hygiene bug.** The merged ADTs, mapper/ordinal/tenor functions, options record and its `default<Name>` value are exactly what the splice site then refers to by hand, so `newName` would make them unreferenceable. `newName` belongs only on pattern variables inside generated clauses.
- **Pass a spec record, not positional arguments.** `CrossEnumSpec`/`IborConstructorSpec` exist because the old five- and seven-argument forms were runs of interchangeable `String`s and `Name`s where a transposition type-checked and silently generated the wrong code. Give any new `derive*` entry point the same treatment.

## Documentation upkeep

- `QuantLib/Internal/Type.hs` carries a haddock ASCII tree directly above **every** hierarchy root's `type Xxx = GenXxx CXxx`/`newtype GenXxx a` declaration (`CalibratedModel`, `TermStructure`, `Instrument`, …), listing every member indented by parent/child, with `: InterfaceY` suffixes for secondary ADT interfaces (`HullWhite: AffineModel`). Update the relevant tree whenever you add a type to any hierarchy — it's the only place each hierarchy's full shape is written down, and it rots silently.
- `tools/ql-methods-1.43.txt` (the current version's tracking dump): set the affected lines to `v`/`u` as soon as you add a method/class binding — see the `add-quantlib-method` skill for the status vocabulary. Don't let it drift and rely on a bulk resync later.
- README.md's `# TODO`: when finishing a feature, remove any item it resolves.
- `main/test/QuantLib/MainTest.hs` is a thin dispatcher (`hspec $ do X.spec; Y.spec; ...`), not a 1400-line `do` block: each topic's `describe` blocks live in their own `QuantLib.Spec.*` module under `main/test/QuantLib/Spec/`, grouped by what they test (dates/schedule, calendars, currency/day-counter, interest-rate/cash-flow, term-structure, the `*Example` blocks, …), with shared arbitrary instances and comparison helpers (`listClose`, `closePrec`, `ValidDay`, …) in `QuantLib.Spec.Helpers`. A block that needs a value computed once in `main` before `hspec` (e.g. `today`) takes it as an explicit argument to `spec` rather than recomputing it. Add new `describe` blocks to the module matching their topic; don't grow `MainTest.hs` itself back into one file.
- When something took real effort to get right — a non-obvious root cause, a design that took several wrong turns, a gotcha that cost debugging time — write it up before moving on: a skill if it's a repeatable procedure (`add-quantlib-adt`), a CLAUDE.md bullet if it's a standing constraint (the `{#pointer#}` bullet above).

## Editor tooling (`hie.yaml`)

- The cabal multi-cradle maps all of `test/` to `hasquant:test:hasquant_test`, with only `main/exe/QuantLib/MainExample.hs` on `hasquant:exe:hasquant_example`. (`test/` is a shared `hs-source-dirs` of both components; the `hasquant-examples` internal library that would have separated them was reverted — it broke `stack haddock`.) Don't map individual `test/QuantLib/Example/*.hs` files to the exe component (an earlier uncommitted attempt did): ghcide registers *every* target of whichever component loads first as that component's home modules, so once an Example file opens under the exe, `main/test/QuantLib/MainTest.hs` fails to typecheck with `attempting to use module ... which is not loaded` (GHC-58427) — the same physical files now belong to two live HscEnvs in one session. Routing shared files through one component minimises this; opening `MainExample.hs` alongside a test file still triggers it (residual, accepted — the exe target is niche and flag-gated).
- `exe:hasquant_example` is `buildable: False` unless `flag(buildExample)` is set, so HLS on `main/exe` needs `package hasquant / flags: +buildExample` in the local, gitignored `cabal.project.local`. Without it hie-bios reports `Cannot build the executable ... marked as 'buildable: False'`.
- Cabal's target for the main library is `lib:hasquant` or bare `hasquant`, never `hasquant:lib` (`Unknown target 'hasquant:lib'`) — this was a live bug in `hie.yaml`'s `QuantLib/` entry.
