# hasquant

Haskell bindings to QuantLib via c2hs, with a C++ shim layer in `cbits/`.

## Development

- This codebase has accumulated many special-case patterns for recurring problems (c2hs cross-module enum-import cycles, multi-inheritance secondary interfaces, wide-arity constructors, etc. — see the bullets below and the `.claude/skills/` directory). Before introducing a new workaround for a problem that feels novel — a hand-rolled type mirroring a C enum, a new module, a new abstraction layer — grep the codebase (and this file) for how a similarly-shaped problem was already solved; a plausible-looking one-off fix is more likely a rediscovery of an existing pattern than a genuinely new case, and diverging from the established pattern (e.g. `QuantLib.Internal.Enum`'s existing "avoid cyclic deps" home for cross-cutting enums like `TimeUnit`) both duplicates effort and drops the safety properties the established pattern already has (see the `CPIInterpolationType` case below, first hand-rolled outside that pattern, then moved back into it).
- To test C++-only changes quickly (without a full Haskell rebuild), run `make`.
- To build and run the full test suite, use `stack build --test --no-haddock`.
- Once testing is complete, make sure you haven't introduced any new compilation warnings, and run `hlint` and fix its warnings. Don't apply an hlint suggestion without checking it actually holds: two of its hints have already turned out to be wrong here. `Avoid NonEmpty.unzip` fires on the bare name `unzip` in *any* module that imports `Data.List.NonEmpty`, with no type resolution at all — it flags plain `Prelude.unzip` over ordinary lists, and importing `Data.Functor.unzip` explicitly doesn't silence it. When a hint is genuinely wrong, add a targeted `- ignore: {name: ..., within: Module}` to `.hlint.yaml` with the evidence in a comment, rather than contorting the code; the goal is a clean `hlint` run so real hints stay visible.
- The package supports **GHC 8.10.6 / base 4.14** (`hasquant.cabal` declares `base >=4.11`), verified via the lts-18.8 Docker image. Nothing merges until this passes:
  `docker compose run --rm hasquant sh -c 'stack build --resolver lts-18.8 --flag hasquant:buildExample --no-haddock && stack --resolver lts-18.8 test'`
  (note: no `-it`, which fails without a TTY). This gate catches two classes of problem the local GHC 9.10 build cannot. First, post-8.10 `base` functions creeping in — often *via* an hlint suggestion, e.g. `Data.Functor.unzip` (base 4.19+). Second, inferred types that 9.10 accepts and 8.10 rejects: a `let`-bound helper containing a list literal under `OverloadedLists` over-generalised to an `IsList`-polymorphic type and failed with `Illegal equational constraint` (fix: give the helper an explicit signature).
- Slow tests are marked by suffixing `(LONG)` to the `it`/`describe` description string; `stack test --ta '--skip LONG'` is the fast path (0.8s vs 21s for the full suite). The effective threshold is ~2.5s, not tens of seconds — measure before labelling rather than assuming, and re-check existing labels (the equity option block was labelled `(LONG)` while running in 0.5s).
- When picking a tolerance for a numeric assertion, scale it to the magnitude of the value (~1e-6 relative), don't pin it at 1e-6 absolute. Bootstrapped curve results and optimiser-calibrated model parameters differ in the last few places between platforms — the aarch64/macOS and x86_64 container builds disagree at ~1e-4 on the CDS survival probabilities and the G2 calibrated parameters — so an absolute 1e-6 on a value of magnitude 1e4 isn't a stricter test, just one that fails the lts-18.8 gate. Recording a value at more digits and tightening its tolerance are separate decisions.
- When writing a new `test/QuantLib/Example/*.hs` port or picking verification numbers for one, check `~/Src/QuantLib/test-suite/*.cpp` first for an existing upstream test covering the same class/scenario — it often has real, already-cached expected values (e.g. `inflationcpibond.cpp`'s `testCleanPrice` gives exact `dirtyPrice`/`cleanPrice` figures for a `CPIBond`) that are stronger and cheaper to reuse than hand-deriving or self-consistency-only checks. Match the upstream fixture (index, calendar, schedule, quotes) closely enough that the cached numbers actually apply. Only fall back to a self-consistency check (e.g. "reprices to its own fair rate") when no upstream test exercises the class directly — confirm via `grep` for the class's constructor call across `test-suite/*.cpp` before assuming one doesn't exist.
- Editing a C header (e.g. `cbits/qlEnumObjects.h`) without touching any `.chs` file can leave `cabal build`/`stack build` silently stale — neither tracks that a `.chs` file's `#include`d header changed, so it may report success without re-running c2hs, and tests will then pass against the *old* generated code. If in doubt, do a clean build. See `smoke/` for standalone end-to-end value-level checks (run via `cabal exec -- ghc -package hasquant smoke/Foo.hs -o /tmp/foo && /tmp/foo`) — a compiled build is not proof that generated enum cases actually changed.
- Keep `smoke/` up to date: whenever you add an enum-dispatched case (a new currency, calendar, or index variant — see the `reconcile-*`/`add-quantlib-index` skills), add or extend a script there that constructs the new case and prints something derived from it, and actually run it. This is what catches the staleness gotcha above and any enum/factory-table order mismatch — the formal test suite under `test/` won't, since it doesn't know about cases it was never written to check.
- When you add a method/class binding, update the corresponding line(s) in `tools/ql-methods-1.43.txt` (the current version's tracking dump) to `v`/`u` right away — see the `add-quantlib-method`/`add-quantlib-class` skills for the exact status vocabulary. Don't let it drift out of sync and rely on a bulk resync script to catch up later.
- Don't expose `QuantLib.Internal.*` modules (moving them from `other-modules` to `exposed-modules`) to work around a c2hs cross-module `{#import#}` ordering problem — this only affects **enum** types referenced inside a `{#fun#}` binding in another module, since `{#import Module#}(Type)` needs that module's `.chi` file to already exist, and `other-modules` isn't part of the ordered-by-list-position scheme `exposed-modules` uses (reordering, even fully serial `-j1` builds, doesn't fix it). Avoid the problem instead: add dedicated, specific constructors that hardcode the enum value inside their own C++ shim function (e.g. `ActualActualBond' :: Schedule -> DayCounterConstructor`) rather than one generic constructor taking the enum as an argument — see the `reconcile-daycounters` skill's `ActualActual` case. This sidesteps the issue entirely, since no enum then crosses a module boundary. If a case genuinely needs a parameterized enum passed through (rare): marshal that field as a plain `Int`/`CInt` in the low-level, unexported `{#fun#}` glue binding only, converting via `fromEnum` at its one call site — the public constructor stays fully typed. Pointer/foreign-type fields (like `Schedule`) never hit this: just locally re-declare a `{#pointer#}` for the type in the file that needs it, the way `Schedule` already is in several `.chs` files.
- Don't export c2hs's raw, double-underscore-prefixed enum constructor names (e.g. `ActualActual__Bond` from `{#enum ActualActualConvention{} add prefix = "ActualActual__"#}`) through any public module — they read as internal/generated, not like the rest of the library's API. If a case needs to be user-facing, give it a proper dedicated constructor/name instead (see the point above) rather than exporting the enum type itself.
- `{#pointer#}` pragma flags decide what a bare-backtick `{#fun#}` return spec (`` ->`T' `` with no named out-marshaller) actually produces, and picking the wrong combination compiles-then-crashes or fails type-checking in confusing ways rather than erroring at the pragma itself:
  - `{#pointer *T foreign finalizer F newtype#}` (c2hs owns the type) auto-generates a `ForeignPtr`-wrapped newtype `T` with finalizer `F`; a bare `` ->`T' `` then auto-wraps the raw returned C pointer into `T`.
  - `{#pointer *T foreign -> X nocode#}` (used when `T`'s `Finalizable`/`Upcastable` instances are hand-written elsewhere, e.g. in `QuantLib/Internal/Type.hs` — the pattern for every class hierarchy: Option, Quote, Bond, Payoff/Exercise, etc.) tells c2hs `T` denotes a `ForeignPtr`-managed value shaped like `X`, but suppresses generating the wrapper. A bare `` ->`T' `` still tries to auto-wrap into a `ForeignPtr` — which fails (`Couldn't match type 'ForeignPtr X' with '...'`) unless `T` actually is that shape.
  - `{#pointer *T nocode#}` (bare — no `foreign`, no `-> X`) is what you want for a genuinely raw, un-wrapped `Ptr T` (e.g. to hand off for further hand-written `Upcastable` upcasting rather than a fully-materialized value). A bare `` ->`T' `` here does *not* do the obvious thing either — it marshals `T` *by value*, and GHC rejects it (`T cannot be marshalled in a foreign call`). c2hs has no built-in identity/passthrough out-marshaller, so you must write one and name it explicitly: `peekPtr :: Ptr a -> IO (Ptr a); peekPtr = pure`, then `` ->`T'peekPtr* ``.
  - Every `Ql*AsY` "upcast" shim in `cbits/` (for both the Payoff/Exercise hierarchy and every `Upcastable`-based one) is `ret(new QlY(*arg(o)))` — a fresh, independently-owned handle sharing the underlying QuantLib object via `shared_ptr` refcounting, not a non-owning pointer reinterpretation. This is exactly the ownership pattern `Upcastable`/`AnyOf`/`freeUpcast` assume (free the upcast intermediate immediately after the consuming call returns) — safe to reuse for a new hierarchy edge without re-deriving this from scratch.
- `hie.yaml`'s cabal multi-cradle maps `test/` (shared `hs-source-dirs` of both `exe:hasquant_example` and `test:hasquant_test`, since `hasquant-examples` internal-library was reverted — it broke `stack haddock`) entirely to `hasquant:test:hasquant_test`, with only `main/exe/QuantLib/MainExample.hs` pointing at `hasquant:exe:hasquant_example`. Don't map individual `test/QuantLib/Example/*.hs` files to the exe component (an earlier uncommitted attempt did this) — ghcide registers *every* target of whichever component loads first as that component's home modules, so once any Example file opens under `exe:hasquant_example`, `main/test/QuantLib/MainTest.hs` (always `test:hasquant_test`) fails to typecheck with `attempting to use module ... which is not loaded` (GHC-58427), because the same physical files now belong to two live HscEnvs in one ghcide session. Routing every shared file through one component minimizes how often two components load in the same session; opening `MainExample.hs` together with any test-suite file still triggers this (residual, accepted — the exe target is niche and flag-gated). Also: `exe:hasquant_example` is `buildable: False` unless `flag(buildExample)` is set, so HLS on `main/exe` needs `package hasquant / flags: +buildExample` added to the local, gitignored `cabal.project.local` — a fresh checkout without that stanza gets `Cannot build the executable ... marked as 'buildable: False'` from hie-bios. And cabal's target syntax for the main library is `lib:hasquant` or bare `hasquant`, *not* `hasquant:lib` (that form errors `Unknown target 'hasquant:lib'`) — this was a live bug in `hie.yaml` for the `QuantLib/` entry.
- When finishing a feature, check README.md's `# TODO` section for an item it resolves and remove it.
- When a feature or refactor took noticeable effort to get right — a non-obvious root cause, a design that took several wrong turns before landing, a gotcha that cost real debugging time — consider writing up the finding as a skill (if it's a repeatable procedure, e.g. `add-quantlib-adt`) or a CLAUDE.md bullet (if it's a standing constraint/gotcha, e.g. the `{#pointer#}` bullet above) before moving on. Future sessions (yours or someone else's) shouldn't have to re-derive it from scratch.
- When a QuantLib class multiply-inherits two bases — one that's its real single-parent slot in an existing hasquant hierarchy (e.g. `CalibratedModel`), and a second interface needed only by one consumer (e.g. `AffineModel`, needed only by `analyticCapFloorEngine`; or `Gaussian1dModel`, needed only by `Gaussian1dSwaptionEngine`) — don't add a second `Upcastable` node for the secondary interface. `Upcastable` is single-parent (one `Base` per type), so a second real base has nowhere to go in that scheme. Instead mirror the existing `AffineModel` pattern in `QuantLib/Internal/Type.hs` (search `CAffineModel'`): keep the leaf's one real `Upcastable` instance pointed at its true hierarchy parent, and separately add a standalone (non-`Upcastable`) `qlXAsInterfaceY :: Ptr CX' -> IO (Ptr CInterfaceY')` upcast shim per leaf, plus a hand-written nested ADT (`data InterfaceY = X X | Z Z`) with a `withInterfaceY` function that pattern-matches and calls `withUpcast qlXAsInterfaceY f` per case. The consuming engine/function then takes the concrete ADT value directly (`` withInterfaceY*`InterfaceY' ``), not a polymorphic `GenXxx m` type — see `analyticCapFloorEngine`'s `` withAffineModel*`AffineModel' ``. Usually ADT adaptor is used to pass the object as an argument to methods. Common/overloaded methods are mostly modelled as type classes (`HasImpliedVol`, `HasQuanto`)
- `QuantLib/Internal/Type.hs` has a haddock comment directly above each hierarchy root's `type Xxx = GenXxx CXxx`/`newtype GenXxx a = ...` declaration (e.g. `type CalibratedModel = ...`, `type TermStructure = ...`, `type Instrument = ...`) — an ASCII tree listing every member of that hierarchy, indented to show parent/child, with `: InterfaceY` suffixes marking any secondary ADT interface a member also implements (e.g. `HullWhite: AffineModel`). This applies to **every** hierarchy root in the file, not just the one you happen to be touching. Update the relevant comment every time you add a new type to any of these hierarchies — it's the only place each hierarchy's full shape is written down in one spot, and it silently rots if a new leaf's `Upcastable`/`Finalizable` wiring isn't reflected in it too.
- We rarely bind inspector/getter methods beyond what scheduling/pricing/output actually needs — e.g. `Schedule` binds only `dates` out of ~20 upstream inspectors, `Calendar` binds none of its 4 pure inspectors (`empty()`/`name()`/`addedHolidays()`/`removedHolidays()`), and `Currency` binds a curated 5 of 10 rather than all of them. Setters are bound only for a few justified cases — engine/pricer wiring (`setPricingEngine`, `setCouponPricer(s)`), the global `Settings` singleton, and `SimpleQuote.setValue` (inherently mutable by design) — not as general field mutators. When a new field is genuinely needed, prefer adding a targeted getter (as with `FxForward`'s `fairForwardRate`/`npvSourceCurrency`/`npvTargetCurrency`) over binding every inspector the C++ class happens to expose, and prefer constructing a new object over mutating an existing one (e.g. bake a flag into a constructor rather than adding a post-construction setter for it). Confirm with the user before adding *any* new setter/mutator, even mid-exploration — don't rely on self-judging it against this rule.
- Don't mirror QuantLib's C++ class hierarchy 1:1 in the Haskell layer. If a bound class has no calculations of its own and is never needed as an argument type elsewhere, it doesn't need a dedicated Haskell object/pointer type — a constructing function that builds and returns the parent (or grandparent) type directly is enough. This is already how pricing engines work: `discountingSwapEngine`, `blackCapFloorEngine`, etc. all return the generic `PricingEngine` type, not a dedicated `DiscountingSwapEngine`/`BlackCapFloorEngine` type, since nothing needs the more specific type back. Only introduce a dedicated type (as with `FxForward`'s `fairForwardRate`/`npvSourceCurrency`/`npvTargetCurrency`, or `ForwardRateAgreement`'s `forwardRate`) when the class actually has its own calc/getter or must be passed around as its own type. This applies to module *placement* too: group a new binding with its topically-related family (e.g. `FxForward` lives in `QuantLib/Instrument/Forward.chs` alongside `ForwardRateAgreement`/`BondForward`) rather than a generic hierarchy-root file, even when the C++ inheritance doesn't literally match.
- Same idea one level down: don't bind a constructor function for a C++ class whose constructor(s) do nothing but immediately delegate to a more complex constructor with no logic of its own (e.g. QuantLib's `FixedVsFixedSwap`-style thin convenience subclasses) — bind straight through to whatever it actually constructs instead of adding a pass-through wrapper on our side.
- QuantLib's `Period` has no dedicated Haskell/C type in hasquant — it's always marshalled as a plain `(Int, TimeUnit)`/`(Word, TimeUnit)` tuple via `fromEnumQuantity` (e.g. `addPeriod`, `forwardRateForPeriod`, `swaptionHelper`'s `maturity`/`length`/`fixedLegTenor`), with the C shim taking two plain `int`s and constructing `Period(len, (TimeUnit)unit)` on the C++ side. Similarly, a bond price paired with its `Bond::Price::Type` (clean/dirty) is marshalled as a plain `(Double, BondPriceType)` tuple via `fromEnumDouble` (e.g. `Bond.yield`, `yieldFromPrice`, `zSpread`). Reuse these tuple conventions rather than introducing dedicated wrapper types for either.
- For a constructor/method with a genuinely long trailing-defaulted-param list (roughly `OISRateHelper`-scale, ~19+ params, not a handful), don't widen the existing narrow binding in place the way most `|u|`-status bindings are widened. Instead leave the narrow binding's signature untouched and add a *second*, full-arity entry point whose trailing params are bundled into a TH-generated "options record" (`deriveOptionsRecord` in `QuantLib.Internal.Syntax`), pre-populated with upstream's own defaults via a generated `default<Name>` value, overridden through record-update syntax — see `QuantLib/TermStructure/Yield.chs`'s `OISRateHelperOpts`/`oisRateHelperFull`/`oisRateHelperFull'` for the worked example. `deriveOptionsRecord` takes explicit field names/types/default-exprs at the splice site rather than reifying the target function's type — the underlying binding can have distinct trailing params each carrying their own independent type variable (e.g. `fixedRate :: GenQuote a` vs. `overnightSpread :: Maybe (GenQuote m)`), and correctly re-deriving which of a reified `ForallT`'s bound variables belong on the generated record has no precedent in this module (`deriveCrossEnum`/`deriveIborConstructor` only reify enum/data-constructor shapes, never a function type) — explicit types at the splice site sidestep that, and the type checker still catches drift at the hand-written wrapper. Two related gotchas hit while building this: (1) any record field whose type mentions a fresh type variable (not otherwise in scope) must be built via `varT`/`$(...)` antiquotation inside the `[t| |]` quote, not a bare lowercase identifier — TH type quotes don't auto-quantify free variables the way an ordinary type signature does; (2) the `$(deriveOptionsRecord ...)` splice must be placed *before every* `{#fun#}` hook in the `.chs` file (e.g. right after the file's pointer/enum declarations), never in between two of them — c2hs always appends its raw `foreign import` stubs at the physical end of the generated module regardless of where a `{#fun#}` hook appears in the source, and a top-level TH splice anywhere else splits the file into declaration groups that can't see each other, breaking every earlier `{#fun#}` wrapper's reference to its own (always-last) foreign-import stub. A record's field types that need a live IO-constructed value with no pure default (e.g. `Calendar`, which only exists via `calendar Null :: IO Calendar`) should be `Maybe`-wrapped with a `Nothing` default; the hand-written wrapper substitutes the real value via `fromMaybe` when the field is `Nothing`. Reserve this pattern for genuinely wide signatures — for the common case (a handful of trailing params), widening the existing narrow binding in place, per the rest of this file, is still the default.
- When a `cbits/qlEnumObjects.h` enum mirrors an upstream QuantLib enum that skips a deprecated leading case (e.g. `CPI::InterpolationType`'s `AsIndex = 0, Flat = 1, Linear = 2`), give the hasquant-side C enum those exact same explicit values (`CPIFlat = 1, CPILinear = 2`) rather than renumbering from 0 — a renumbered-from-0 enum silently aliases each hasquant case to upstream's *next lower* case (hasquant's `CPIFlat` casting to upstream's deprecated `AsIndex`, `CPILinear` to upstream's `Flat`), which can compile and pass a build with no warning since the C++ cast is unchecked. This exact bug shipped undetected for a full earlier session because nothing exercised both enum cases together and compared results numerically. Guard any such enum with a `smoke/` check that constructs both cases from identical inputs and asserts the outputs actually differ (see `smoke/CheckInflation.hs`'s Flat-vs-Linear NPV check) — a same-value smoke-test check is what actually catches this, not a comment. Keep the fix on the C/C++ side (the header's values, and the one hand-written Haskell marshaller function if one already exists for that enum) rather than introducing a new Haskell-side abstraction/module for it.
- Typeclasses are fine, even normal, as *internal* plumbing — `Finalizable`/`Upcastable` in `QuantLib/Internal/Type.hs` are used throughout for the pointer-hierarchy machinery, and nothing about that is discouraged. But think twice before letting one show up in a *public* function signature (a constraint an end user has to satisfy, or a class they'd need to write instances for) — public APIs here favor concrete, dedicated types and functions (see the dedicated-constructor points above) over ad-hoc polymorphism, even at the cost of a few more near-duplicate functions.
