# hasquant

Haskell bindings to QuantLib via c2hs, with a C++ shim layer in `cbits/`.

## Before inventing a workaround

This codebase has accumulated many special-case patterns for recurring problems (c2hs cross-module enum-import cycles, multi-inheritance secondary interfaces, wide-arity constructors). Before adding a hand-rolled type mirroring a C enum, a new module, or a new abstraction layer, grep this file, the codebase, and `.claude/skills/` for how a similarly-shaped problem was already solved. A plausible-looking one-off fix is usually a rediscovery, and diverging from the established pattern drops that pattern's safety properties — e.g. `CPIInterpolationType` was hand-rolled outside `QuantLib.Internal.Common` (the existing home for cross-cutting enums like `TimeUnit`, which live there to avoid cyclic deps) before being moved back into it.

## API design

- **When adding a new binding, consider a neighboring one if it's low-effort and doesn't context-switch.** Minimalism (bind only what's asked) is still the default, but a sibling that reuses plumbing you just built — same marshalling shape, same fixture, same header already open — is often nearly free. `InterpolatedSwaptionVolatilityCube` alongside `SabrSwaptionVolatilityCube` is the model: it reused every piece of the SABR cube's `Handle`/tenor/`Matrix`/`SwapIndex` marshalling and needed no new infrastructure. If the neighbor needs its own investigation, its own fixture, or a genuinely different marshalling shape, it's a separate task.
- **Avoid `dynamic_cast`/`dynamic_pointer_cast` in `cbits/` unless upstream's own architecture forces it** (e.g. a base-class API upstream itself only reaches via downcast, with no compile-time-typed alternative). Prefer a dedicated Haskell leaf type with its own concrete-pointer-typed getters — compile-time type safety beats a runtime cast that can throw on the wrong producer. `cbits/` has had zero `dynamic_cast`/`dynamic_pointer_cast` call sites since `SabrInterpolatedSmileSection` was converted this way. Derived→Base (upcasting, e.g. a leaf type's `AsSmileSection`/`AsSwaptionVolatilityStructure` escape hatch via a fresh `shared_ptr` construction) is always safe and never needs a cast; it's Base→Derived that this rule targets.
  - **The fix is usually "promote the accessor's return type to a real family, one more `AnyOf` layer deep" — not a cast at the point that needs the concrete type.** `SwaptionHelper::underlying()`/`swaption()` are `SwaptionHelper`-specific (not on the `BlackCalibrationHelper` base), and `swaptionHelper`'s own C++ shim already knows it is constructing a real `SwaptionHelper` — so instead of erasing to generic `BlackCalibrationHelper` at construction and `dynamic_pointer_cast`-ing back for these two getters, `SwaptionHelper` was made a real one-`AnyOf`-layer-deeper leaf under `BlackCalibrationHelper` (mirrors `GenMultiAssetOption`/`MargrabeOption` under `GenOption`, and `GenSwap`/`VanillaSwap` under `GenInstrument`): `type GenBlackCalibrationHelper bch = GenCalibrationHelper (AnyOf CBlackCalibrationHelper' bch)`, `BlackCalibrationHelper = GenBlackCalibrationHelper CBlackCalibrationHelper`, `SwaptionHelper = GenBlackCalibrationHelper CSwaptionHelper`. `underlying`/`swaption` then take the concrete `SwaptionHelper` pointer directly — genuinely cast-free, since the object handed to the C shim already *is* a `SwaptionHelper`, not something erased that needs rediscovering. The pre-existing base-level accessors (`times`, `blackPrice`, `impliedVolatility`, `marketValue`, `modelValue`, `setPricingEngine`, and the new `volatility`) were generalized from the concrete `BlackCalibrationHelper` to `GenBlackCalibrationHelper bch` so they keep working on `SwaptionHelper` (or any future leaf) without an explicit upcast at the call site.
  - **Root vs. leaf peek differs even after this promotion, and getting it backwards produces a confusing double-upcast, not a compile error.** A family *root at its own concrete type* (`BlackCalibrationHelper` used as itself, `MultiAssetOption` used as itself) peeks with `newCastForeignPtr` (no upcast — the C shim already erased to exactly that type at construction). A *leaf* one level under it (`SwaptionHelper`, `MargrabeOption`, `VanillaSwap`) peeks with `newGenForeignPtr` (upcasts via `Upcastable` on access). Promoting `BlackCalibrationHelper` from "leaf directly under `CalibrationHelper`" to "root of its own one-`AnyOf`-layer family" flips its own peek function from `newGenForeignPtr` to `newCastForeignPtr` — easy to miss since both compile either way (the extra/missing upcast just silently walks one hierarchy level too far or not far enough at runtime). `peel` count follows the same root/leaf split: a root's own `with*`/`peekPtrArray`-style array helper needs `peel` for each `AnyOf` layer already under it (`withBlackCalibrationHelperArray` needed 1 `peel` once `BlackCalibrationHelper` itself moved from 0 layers to 1); a same-depth leaf uses the identical `peel` count as the root, differing only in which concrete type occupies the innermost slot (`VanillaSwap` and `FixedVsFloatingSwap`-as-itself both need 2 `peel`s under `GenInstrument`, matching `MargrabeOption`/`MultiAssetOption`'s existing 2).
  - **An upstream accessor returning a *different* base than the one your leaf currently upcasts to is the other trigger for widening a family**, independent of any cast question. `SwaptionHelper::underlying()` returns `FixedVsFloatingSwap`, not `VanillaSwap` — `VanillaSwap` upcast straight to `Swap` before this, collapsing the intermediate C++ level (the normal, correct default per "don't mirror the hierarchy 1:1"). Getting `underlying()`'s real return type bound at all meant giving `FixedVsFloatingSwap` the same one-more-`AnyOf`-layer treatment (`GenFixedVsFloatingSwap f = GenSwap (AnyOf CFixedVsFloatingSwap' f)`, `VanillaSwap = GenFixedVsFloatingSwap CVanillaSwap`) and moving `VanillaSwap`'s own inherited getters (`fairRate`, `fairSpread`, `fixedLeg*`, `floatingLeg*` — all genuinely declared on `FixedVsFloatingSwap` upstream, not `VanillaSwap`) to take `GenFixedVsFloatingSwap f` generically, exactly mirroring the `BlackCalibrationHelper` move above. `FixedVsFloatingSwap` itself binds no constructor (pure-virtual `setupFloatingArguments` upstream), so it only ever appears as an accessor return type or an upcast target — that's still enough to need the full family machinery, not just a type alias.
  - **A C++ return type erased *by upstream itself*, before your shim ever sees it, cannot be recovered by any of the above — check this before promising an accessor.** `NonstandardSwaption::calibrationBasket` returns `vector<shared_ptr<BlackCalibrationHelper>>`; `basketgeneratingengine.cpp` always constructs `SwaptionHelper` internally, but the erasure to the base already happened inside QuantLib's own code before the vector is returned, so basket elements are genuinely, only `BlackCalibrationHelper` by the time hasquant's shim wraps them — `underlying`/`swaption`/the `SwaptionHelper` leaf type are reachable only for helpers hasquant itself constructs (`swaptionHelper`/`swaptionHelperFromDate(s)`), never for basket elements. Confirm this by reading the upstream `.cpp` (not just the header) for the concrete type actually constructed, before assuming a cast — dynamic or `static_pointer_cast` — could close the gap; here it's not a cast problem, it's a fact about what information upstream already discarded.
- **Don't mirror QuantLib's C++ hierarchy 1:1.** A bound class with no calculations of its own, never needed as an argument type elsewhere, doesn't need a Haskell object/pointer type — a constructing function returning the parent (or grandparent) is enough. That's already how pricing engines work: `discountingSwapEngine`, `blackCapFloorEngine` etc. all return the generic `PricingEngine`. Introduce a dedicated type only when the class has its own calc/getter (`FxForward`'s `fairForwardRate`, `ForwardRateAgreement`'s `forwardRate`) or must be passed around as its own type. Same idea one level down: don't bind a constructor for a class whose constructors only delegate to a more complex one with no logic of their own (QuantLib's `FixedVsFixedSwap`-style thin convenience subclasses) — bind straight through to what it actually constructs.
- **Module placement follows the topical family, not C++ inheritance.** `FxForward` lives in `QuantLib/Instrument/Forward.chs` alongside `ForwardRateAgreement`/`BondForward`, though it isn't a C++ `Forward` subclass. Leave the generic root module (e.g. `QuantLib/Instrument.chs`) for hierarchy-wide methods.
- **Bind few inspectors** — only what scheduling/pricing/output needs. `Schedule` binds `dates` out of ~20 upstream inspectors, `Calendar` binds none of its 4 (`empty()`/`name()`/`addedHolidays()`/`removedHolidays()`), `Currency` a curated 5 of 10. Prefer one targeted getter (as with `FxForward`'s `fairForwardRate`/`npvSourceCurrency`/`npvTargetCurrency`) over binding everything the C++ class exposes.
- **Setters** exist only for engine/pricer wiring (`setPricingEngine`, `setCouponPricer(s)`), the global `Settings` singleton, and `SimpleQuote.setValue` (mutable by design) — not as general field mutators. Prefer constructing a new object over mutating one (bake a flag into a constructor rather than adding a post-construction setter). **Confirm with the user before adding any new setter/mutator**, even mid-exploration — don't rely on self-judging it against this rule.
- **Typeclasses** are fine, even normal, as *internal* plumbing — `Finalizable`/`Upcastable` in `QuantLib/Internal/Type.hs` are used throughout. Think twice before one appears in a *public* signature as a constraint the user must satisfy: public APIs here favour concrete, dedicated types and functions over ad-hoc polymorphism, even at the cost of a few near-duplicate functions.
- **`GenForeignPtr`'s `_access`/`_mayFree` fields are a deliberate manual dictionary, not a missed abstraction.** An `Access a b` class would shrink `GenForeignPtr` to a coercible newtype, but c2hs emits an explicit type signature for **every** `{#fun#}`, so the constraint cannot be inferred in: **363 of 880** hooks take a polymorphic `` `GenX a' `` and would each need a hand-written context. c2hs's `CHSFun` type context is backtick-verbatim, and that form terminates on `'`, so a context mentioning `CQuote'` would need a prime-free constraint synonym per hierarchy level. It would also put a constraint in public signatures (against the rule above) and buys no correctness — `newCastForeignPtr` and `newGenForeignPtr` are already pinned by their result types.
- **`Period` has no dedicated type** — always marshalled as a plain `(Int, TimeUnit)`/`(Word, TimeUnit)` tuple via `fromEnumQuantity` (`addPeriod`, `forwardRateForPeriod`, `swaptionHelper`'s `maturity`/`length`/`fixedLegTenor`), with the C shim taking two plain `int`s and constructing `Period(len, (TimeUnit)unit)`. A bond price paired with its `Bond::Price::Type` is likewise a `(Double, BondPriceType)` tuple via `fromEnumDouble` (`Bond.yield`, `yieldFromPrice`, `zSpread`). `Money` is the same idea one type wider: a `(Double, Currency)` tuple whose second component is a foreign-pointer type rather than an enum, so it needs a `withX`-style continuation marshaller instead of a pure function — `withMoney :: (Double, Currency) -> ((CDouble, Ptr CCurrency) -> IO b) -> IO b` (`QuantLib/Internal/Type.hs`), used with c2hs's `&` splitter exactly like `withDoubleArray*`[Double]'&` (`exchange`, `convertToBaseCurrency` in `QuantLib/Currency.chs`). Reuse these tuple conventions rather than introducing wrapper types, and keep the convention symmetric: if a function's *output* is a `Money`-shaped tuple, its matching *input* parameter should be the same tuple, not two flattened arguments.
- **`std::variant<Real, Handle<Quote>>` (or `Rate`/`Spread`/`Volatility` in place of `Real`) collapses to a single `GenQuote`-taking function — never bind a second flat-`Double` overload.** A `simpleQuote` is a one-line existing binding (`QuantLib/Quote.chs`), so a caller with only a bare number can get the variant's `Real` alternative for free. Construct the variant alternative on the C++ side from a nullable `Quote*` (ternary idiom: `q ? variant<Real, Handle<Quote>>(*arg(q)) : variant<Real, Handle<Quote>>(Real(0.0))`, see `qlSofrFutureRateHelper`/`qlOISRateHelper` in `cbits/qlTermStructure.cpp`), not from two Haskell-visible functions. Confirmed via `sofrFutureRateHelper`, whose original dual-entry-point design was rejected for exactly this reason.

  Auditing this pattern has two traps. A same-name-sibling grep (`Double' -- ^rate/price/vol/spread/forward` alongside a same-name `GenQuote` function) only catches one `std::variant` function with two Haskell-visible entry points; it misses a plain-number constructor bound while a *separate*, differently-shaped Quote-taking overload sits unbound next to it. Crossing `tools/ql-methods-1.43.txt`'s status column against `Handle<Quote>` occurrences per class found that shape five times — `SabrInterpolatedSmileSection`, `Gsr`, `CounterpartyAdjSwapEngine`, `SwaptionVolatilityMatrix`, `HestonModelHelper` (its `s0` param) — all converted to their Quote overload, with the superseded plain-number tracking line flipped to `x` (permanently excluded) rather than inventing a new status letter. Second, the file's `v`/`u` marks are not reliable evidence of which overload is actually bound: for `FlatForward`, `BlackConstantVol`, `LocalConstantVol`, `ConstantCapFloorTermVolatility`, `ConstantOptionletVolatility`, `ConstantSwaptionVolatility`, `FlatHazardRate`, `CallableBondConstantVolatility`, `BachelierCapFloorEngine`, `BlackCapFloorEngine`, `BlackSwaptionEngine`, `BachelierSwaptionEngine` and `LocalVolSurface`, the plain-number sibling is marked `v` even though only the Quote overload has a real C shim. Check `cbits/*.cpp` directly rather than trusting the mark.
- **Wide constructors.** For the common case (a handful of trailing defaulted params), widen the existing narrow binding in place — every defaulted param becomes a required Haskell argument. Only past **10 trailing defaulted params** (`OISRateHelper`-scale) leave the narrow binding's signature untouched and add a *second*, full-arity entry point whose trailing params are bundled into a TH-generated options record (`deriveOptionsRecord` in `QuantLib.Internal.Syntax`), pre-populated with upstream's defaults via a generated `default<Name>` value. Worked example: `OISRateHelperOpts`/`oisRateHelperFull`/`oisRateHelperFull'` in `QuantLib/TermStructure/Yield.chs`; procedure and gotchas in the `add-quantlib-options-record` skill. (`AmortizingFloatingRateBond`'s 14-param options record and `AmortizingFixedRateBond`'s 8-param widen-in-place, both in `QuantLib/Instrument/Bond.chs`, are the pair this threshold was calibrated against.)
- **Scale a numeric test tolerance to the magnitude of the value** (~1e-6 relative); don't pin it at 1e-6 absolute. Bootstrapped curve results and optimiser-calibrated model parameters differ in the last few places between platforms — aarch64/macOS and the x86_64 container disagree at ~1e-4 on the CDS survival probabilities and the G2 calibrated parameters — so an absolute 1e-6 on a value of magnitude 1e4 isn't a stricter test, just one that fails the lts-18.8 gate. Recording a value at more digits and tightening its tolerance are separate decisions.
- For a new `test/example/QuantLib/Example/*.hs` port, check `~/Src/QuantLib/test-suite/*.cpp` first: an upstream test on the same class/scenario often has real, already-cached expected values (e.g. `inflationcpibond.cpp`'s `testCleanPrice` gives exact `dirtyPrice`/`cleanPrice` for a `CPIBond`), stronger and cheaper than hand-deriving. Match the upstream fixture (index, calendar, schedule, quotes) closely enough that the cached numbers apply. Fall back to a self-consistency check ("reprices to its own fair rate") only after grepping for the class's constructor across `test-suite/*.cpp` and finding nothing.
  - A grep hit isn't automatically usable: check whether the upstream test's *fixture* is buildable from hasquant's current bindings before promising a golden-value comparison, not just whether the class under test is bound. Binding `gaussian1dCapFloorEngine` found a real cross-check at `test-suite/markovfunctional.cpp:1234` (`Gaussian1dCapFloorEngine` vs `BlackCapFloorEngine`, 1bp tolerance) — but it only exercises a `MarkovFunctional` built via its caplet-smile-matching constructor (`iborIndex`/`capletExpiries`/`capletVts`), and hasquant binds only `MarkovFunctional`'s other constructor (swaption/CMS-calibrating, used for the Gaussian1d bermudan-swaption examples). Nothing was erased by upstream here (contrast the `NonstandardSwaption::calibrationBasket` case above) — the reference fixture simply isn't constructible yet, which only shows up by reading past the grep hit to what it actually builds, not by trusting that the class name matched.
- **A Monte Carlo example built on `pathGenerator`/`sobolPathGenerator` needs a fixed nonzero seed before its output can be pinned in a test.** `MersenneTwisterUniformRng` treats seed `0` as "seed from entropy" (`ql/math/randomnumbers/mt19937uniformrng.hpp`), so `seed = 0` (as `test/example/QuantLib/Example/TARF.hs` had) makes every run's paths, and hence its NPV, genuinely different. With a fixed nonzero seed MT19937's integer draw sequence is identical across platforms, so only the FP transform/evolution differs, at the usual ~1e-4–1e-6 relative level.
- **Add a martingale-style self-consistency check alongside any FX/equity process example.** In TARF, comparing the simulated path mean (`simFwds`) against the deterministic discount-curve-implied forward (`implFwds`) — which must match under the risk-neutral measure — showed a persistent one-directional ~1% gap, not MC noise (MC error at that trial count is ~0.04%). The cause was `garmanKohlagenProcess`'s foreign/domestic `YieldTermStructure` arguments passed in the wrong order (ILS as foreign, EUR as domestic, for a spot quoted ILS-per-EUR — EUR is the foreign currency there), flipping the sign of part of the drift.

## c2hs and the C shim

See the `c2hs-shim-patterns` skill for `{#pointer#}` pragma rules, C shim marshalling patterns (`alloca-`/`preArray`), `Handle<YieldTermStructure>` semantics, multiple-inheritance/upcast shims, cross-module enum-import avoidance, and `GenX` mnemonic naming.

- **Avoid raw `foreign import ccall` declarations in binding `.chs` files** — prefer `QuantLib.Internal`/`QuantLib.Internal.Type`/`QuantLib.Internal.Common`, mirroring where their own low-level FFI plumbing (`qlFreeAdditionalResults`, `peekStructArray`, `GenForeignPtr`, ...) already lives. A single, contained, occasional raw call local to one binding module is fine; don't reach for it as a default just because a `{#fun#}` won't fit — that's the shape of problem `Internal`/`Internal.Type`/`Internal.Common` already exist to hold, and scattering raw FFI declarations across binding modules is how a marshaller like `RawResult`/`AdditionalResultVal` ends up hand-rolled in `QuantLib.Instrument` (pulling in five unrelated `Foreign.*` imports) instead of centralized where other cross-cutting marshalling lives.

## Template Haskell (`QuantLib/Internal/Syntax.hs`)

- **Verify any refactor of the `derive*` functions with a `-ddump-splices` diff, not by reading.** Capture the dump before and after, normalise it (strip the `file:line:col` prefixes, collapse TH's `x_a1n2U` unique suffixes to a placeholder), and require the two to be **byte-identical**; that is what pins the things nothing else can see — notably per-field strictness (`Bang NoSourceUnpackedness SourceStrict` for the enum ADTs' `!` fields vs `NoSourceStrictness` for the options records' lazy ones), which no `test/smoke/` script or test can catch because they check values, not strictness. Getting the dump out has its own trap: **neither `touch` nor `stack build --force-dirty` re-triggers it** on an otherwise up-to-date build, because `-ddump-splices` doesn't change the ABI and GHC's recompilation avoidance skips the module — delete the splice modules' `.hi`/`.o` under `.stack-work/dist/*/build/` first, then build with `--ghc-options=-ddump-splices`.
- **The module builds its output as raw `Dec`/`Con`/`Exp`/`Pat` constructors, not quotation brackets or `TH.Lib` combinators** — with two forced exceptions, because `template-haskell` changed their arity *inside* the supported GHC range (8.10's 2.16 through 9.10's 2.22), so a literal application fails at one end or the other: `ConP` gained a `[Type]` field for visible type application in 2.18 (wrapped as the local `conPat`), and `TyVarBndr` gained a flag parameter in 2.17, so `PlainTV` took a second argument (hence `plainTV` surviving in `deriveOptionsRecord`). `TupE` is *not* such a case — it has taken `[Maybe Exp]` since 2.16, across the whole range. Check any newly used TH constructor against both ends before writing it raw; the lts-18.8 gate is the only thing that catches this.
- **`mkName` for generated top-level names is deliberate, not a hygiene bug.** The merged ADTs, mapper/ordinal/tenor functions, options record and its `default<Name>` value are exactly what the splice site then refers to by hand, so `newName` would make them unreferenceable. `newName` belongs only on pattern variables inside generated clauses.
- **Pass a spec record, not positional arguments.** `CrossEnumSpec`/`IborConstructorSpec` exist because the old five- and seven-argument forms were runs of interchangeable `String`s and `Name`s where a transposition type-checked and silently generated the wrong code. Give any new `derive*` entry point the same treatment.

## Documentation upkeep

- `QuantLib/Internal/Type.hs` carries a haddock ASCII tree directly above **every** hierarchy root's `type Xxx = GenXxx CXxx`/`newtype GenXxx a` declaration (`CalibratedModel`, `TermStructure`, `Instrument`, …), listing every member indented by parent/child. The notation is defined once, in the legend under `-- TYPE HIERARCHIES` in that file: `X*` = abstract *here* (hasquant binds no constructor returning an X), `X + Y` = X also reaches secondary interface Y, `X (CFoo')` = X's C type where it isn't the expected `C<X>'` (only `OvernightIborIndex` today). Update the relevant tree whenever you add a type to any hierarchy — it's the only place each hierarchy's full shape is written down, and it rots silently. Payoff/Exercise are documented in their own files, not here. `X*` is not derivable from upstream: `Option` and `Swap` are concrete C++ classes yet unconstructible here, while `Quote`/`Index`/`TermStructure` are pure-virtual upstream yet routinely returned by bindings — so mark it by hand, and don't read an unmarked node as a claim of the opposite.
- `tools/ql-methods-1.43.txt` (the current version's tracking dump): set the affected lines to `v`/`u` as soon as you add a method/class binding — see the `add-quantlib-method` skill for the status vocabulary. Don't let it drift and rely on a bulk resync later.
- README.md's `# TODO`: when finishing a feature, remove any item it resolves.
- `test/main/QuantLib/MainTest.hs` is a thin dispatcher (`hspec $ do X.spec; Y.spec; ...`), not a 1400-line `do` block: each topic's `describe` blocks live in their own `QuantLib.Spec.*` module under `test/hspec/QuantLib/Spec/`, grouped by what they test (dates/schedule, calendars, currency/day-counter, interest-rate/cash-flow, term-structure, the `*Example` blocks, …), with shared arbitrary instances and comparison helpers (`listClose`, `closePrec`, `ValidDay`, …) in `QuantLib.Spec.Helpers`. A block that needs a value computed once in `main` before `hspec` (e.g. `today`) takes it as an explicit argument to `spec` rather than recomputing it. Add new `describe` blocks to the module matching their topic; don't grow `MainTest.hs` itself back into one file.
- When something took real effort to get right — a non-obvious root cause, a design that took several wrong turns, a gotcha that cost debugging time — write it up before moving on: a skill if it's a repeatable procedure (`add-quantlib-adt`, `c2hs-shim-patterns`), a CLAUDE.md bullet if it's a standing constraint (e.g. the "Don't mirror QuantLib's C++ hierarchy 1:1" bullet in API design).

## Editor tooling (`hie.yaml`)

- The cabal multi-cradle maps all of `test/` to `hasquant:test:hasquant_test`, with only `test/exe/QuantLib/MainExample.hs` on `hasquant:exe:hasquant_example`. (`test/` is a shared `hs-source-dirs` of both components; the `hasquant-examples` internal library that would have separated them was reverted — it broke `stack haddock`.) Don't map individual `test/example/QuantLib/Example/*.hs` files to the exe component: ghcide registers *every* target of whichever component loads first as that component's home modules, so once an Example file opens under the exe, `main/test/QuantLib/MainTest.hs` fails to typecheck with `attempting to use module ... which is not loaded` (GHC-58427). Routing shared files through one component minimises this; opening `MainExample.hs` alongside a test file still triggers it (residual, accepted).
- `exe:hasquant_example` is `buildable: False` unless `flag(buildExample)` is set, so HLS on `test/exe` needs `package hasquant / flags: +buildExample` in the local, gitignored `cabal.project.local`. Without it hie-bios reports `Cannot build the executable ... marked as 'buildable: False'`.
- Cabal's target for the main library is `lib:hasquant` or bare `hasquant`, never `hasquant:lib` (`Unknown target 'hasquant:lib'`).
