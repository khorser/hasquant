# hasquant

Haskell bindings to QuantLib via c2hs, with a C++ shim layer in `cbits/`.

## Development

- To test C++-only changes quickly (without a full Haskell rebuild), run `make`.
- To build and run the full test suite, use `stack build --test --no-haddock`.
- Editing a C header (e.g. `cbits/qlEnumObjects.h`) without touching any `.chs` file can leave `cabal build`/`stack build` silently stale — neither tracks that a `.chs` file's `#include`d header changed, so it may report success without re-running c2hs, and tests will then pass against the *old* generated code. If in doubt, do a clean build. See `smoke/` for standalone end-to-end value-level checks (run via `cabal exec -- ghc -package hasquant smoke/Foo.hs -o /tmp/foo && /tmp/foo`) — a compiled build is not proof that generated enum cases actually changed.
- Keep `smoke/` up to date: whenever you add an enum-dispatched case (a new currency, calendar, or index variant — see the `reconcile-*`/`add-quantlib-index` skills), add or extend a script there that constructs the new case and prints something derived from it, and actually run it. This is what catches the staleness gotcha above and any enum/factory-table order mismatch — the formal test suite under `test/` won't, since it doesn't know about cases it was never written to check.
- When you add a method/class binding, update the corresponding line(s) in `tools/ql-methods-1.43.txt` (the current version's tracking dump) to `v`/`u` right away — see the `add-quantlib-method`/`add-quantlib-class` skills for the exact status vocabulary. Don't let it drift out of sync and rely on a bulk resync script to catch up later.
- Don't expose `QuantLib.Internal.*` modules (moving them from `other-modules` to `exposed-modules`) to work around a c2hs cross-module `{#import#}` ordering problem — this only affects **enum** types referenced inside a `{#fun#}` binding in another module, since `{#import Module#}(Type)` needs that module's `.chi` file to already exist, and `other-modules` isn't part of the ordered-by-list-position scheme `exposed-modules` uses (reordering, even fully serial `-j1` builds, doesn't fix it). Avoid the problem instead: add dedicated, specific constructors that hardcode the enum value inside their own C++ shim function (e.g. `ActualActualBond' :: Schedule -> DayCounterConstructor`) rather than one generic constructor taking the enum as an argument — see the `reconcile-daycounters` skill's `ActualActual` case. This sidesteps the issue entirely, since no enum then crosses a module boundary. If a case genuinely needs a parameterized enum passed through (rare): marshal that field as a plain `Int`/`CInt` in the low-level, unexported `{#fun#}` glue binding only, converting via `fromEnum` at its one call site — the public constructor stays fully typed. Pointer/foreign-type fields (like `Schedule`) never hit this: just locally re-declare a `{#pointer#}` for the type in the file that needs it, the way `Schedule` already is in several `.chs` files.
- Don't export c2hs's raw, double-underscore-prefixed enum constructor names (e.g. `ActualActual__Bond` from `{#enum ActualActualConvention{} add prefix = "ActualActual__"#}`) through any public module — they read as internal/generated, not like the rest of the library's API. If a case needs to be user-facing, give it a proper dedicated constructor/name instead (see the point above) rather than exporting the enum type itself.
- `{#pointer#}` pragma flags decide what a bare-backtick `{#fun#}` return spec (`` ->`T' `` with no named out-marshaller) actually produces, and picking the wrong combination compiles-then-crashes or fails type-checking in confusing ways rather than erroring at the pragma itself:
  - `{#pointer *T foreign finalizer F newtype#}` (c2hs owns the type) auto-generates a `ForeignPtr`-wrapped newtype `T` with finalizer `F`; a bare `` ->`T' `` then auto-wraps the raw returned C pointer into `T`.
  - `{#pointer *T foreign -> X nocode#}` (used when `T`'s `Finalizable`/`Upcastable` instances are hand-written elsewhere, e.g. in `QuantLib/Internal/Type.hs` — the pattern for every class hierarchy: Option, Quote, Bond, Payoff/Exercise, etc.) tells c2hs `T` denotes a `ForeignPtr`-managed value shaped like `X`, but suppresses generating the wrapper. A bare `` ->`T' `` still tries to auto-wrap into a `ForeignPtr` — which fails (`Couldn't match type 'ForeignPtr X' with '...'`) unless `T` actually is that shape.
  - `{#pointer *T nocode#}` (bare — no `foreign`, no `-> X`) is what you want for a genuinely raw, un-wrapped `Ptr T` (e.g. to hand off for further hand-written `Upcastable` upcasting rather than a fully-materialized value). A bare `` ->`T' `` here does *not* do the obvious thing either — it marshals `T` *by value*, and GHC rejects it (`T cannot be marshalled in a foreign call`). c2hs has no built-in identity/passthrough out-marshaller, so you must write one and name it explicitly: `peekPtr :: Ptr a -> IO (Ptr a); peekPtr = pure`, then `` ->`T'peekPtr* ``.
  - Every `Ql*AsY` "upcast" shim in `cbits/` (for both the Payoff/Exercise hierarchy and every `Upcastable`-based one) is `ret(new QlY(*arg(o)))` — a fresh, independently-owned handle sharing the underlying QuantLib object via `shared_ptr` refcounting, not a non-owning pointer reinterpretation. This is exactly the ownership pattern `Upcastable`/`AnyOf`/`freeUpcast` assume (free the upcast intermediate immediately after the consuming call returns) — safe to reuse for a new hierarchy edge without re-deriving this from scratch.
- When finishing a feature, check README.md's `# TODO` section for an item it resolves and remove it.
- When a feature or refactor took noticeable effort to get right — a non-obvious root cause, a design that took several wrong turns before landing, a gotcha that cost real debugging time — consider writing up the finding as a skill (if it's a repeatable procedure, e.g. `add-quantlib-adt`) or a CLAUDE.md bullet (if it's a standing constraint/gotcha, e.g. the `{#pointer#}` bullet above) before moving on. Future sessions (yours or someone else's) shouldn't have to re-derive it from scratch.
- We rarely bind inspector/getter methods beyond what scheduling/pricing/output actually needs — e.g. `Schedule` binds only `dates` out of ~20 upstream inspectors, `Calendar` binds none of its 4 pure inspectors (`empty()`/`name()`/`addedHolidays()`/`removedHolidays()`), and `Currency` binds a curated 5 of 10 rather than all of them. Setters are bound only for a few justified cases — engine/pricer wiring (`setPricingEngine`, `setCouponPricer(s)`), the global `Settings` singleton, and `SimpleQuote.setValue` (inherently mutable by design) — not as general field mutators. When a new field is genuinely needed, prefer adding a targeted getter (as with `FxForward`'s `fairForwardRate`/`npvSourceCurrency`/`npvTargetCurrency`) over binding every inspector the C++ class happens to expose, and prefer constructing a new object over mutating an existing one (e.g. bake a flag into a constructor rather than adding a post-construction setter for it). Confirm with the user before adding *any* new setter/mutator, even mid-exploration — don't rely on self-judging it against this rule.
- Don't mirror QuantLib's C++ class hierarchy 1:1 in the Haskell layer. If a bound class has no calculations of its own and is never needed as an argument type elsewhere, it doesn't need a dedicated Haskell object/pointer type — a constructing function that builds and returns the parent (or grandparent) type directly is enough. This is already how pricing engines work: `discountingSwapEngine`, `blackCapFloorEngine`, etc. all return the generic `PricingEngine` type, not a dedicated `DiscountingSwapEngine`/`BlackCapFloorEngine` type, since nothing needs the more specific type back. Only introduce a dedicated type (as with `FxForward`'s `fairForwardRate`/`npvSourceCurrency`/`npvTargetCurrency`, or `ForwardRateAgreement`'s `forwardRate`) when the class actually has its own calc/getter or must be passed around as its own type. This applies to module *placement* too: group a new binding with its topically-related family (e.g. `FxForward` lives in `QuantLib/Instrument/Forward.chs` alongside `ForwardRateAgreement`/`BondForward`) rather than a generic hierarchy-root file, even when the C++ inheritance doesn't literally match.
- Same idea one level down: don't bind a constructor function for a C++ class whose constructor(s) do nothing but immediately delegate to a more complex constructor with no logic of its own (e.g. QuantLib's `FixedVsFixedSwap`-style thin convenience subclasses) — bind straight through to whatever it actually constructs instead of adding a pass-through wrapper on our side.
- Typeclasses are fine, even normal, as *internal* plumbing — `Finalizable`/`Upcastable` in `QuantLib/Internal/Type.hs` are used throughout for the pointer-hierarchy machinery, and nothing about that is discouraged. But think twice before letting one show up in a *public* function signature (a constraint an end user has to satisfy, or a class they'd need to write instances for) — public APIs here favor concrete, dedicated types and functions (see the dedicated-constructor points above) over ad-hoc polymorphism, even at the cost of a few more near-duplicate functions.
