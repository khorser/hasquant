# hasquant

Haskell bindings to QuantLib via c2hs, with a C++ shim layer in `cbits/`.

## Development

- To test C++-only changes quickly (without a full Haskell rebuild), run `make`.
- To build and run the full test suite, use `stack build --test --no-haddock`.
- Editing a C header (e.g. `cbits/qlEnumObjects.h`) without touching any `.chs` file can leave `cabal build`/`stack build` silently stale — neither tracks that a `.chs` file's `#include`d header changed, so it may report success without re-running c2hs, and tests will then pass against the *old* generated code. If in doubt, do a clean build. See `smoke/` for standalone end-to-end value-level checks (run via `cabal exec -- ghc -package hasquant smoke/Foo.hs -o /tmp/foo && /tmp/foo`) — a compiled build is not proof that generated enum cases actually changed.
- Keep `smoke/` up to date: whenever you add an enum-dispatched case (a new currency, calendar, or index variant — see the `reconcile-*`/`add-quantlib-index` skills), add or extend a script there that constructs the new case and prints something derived from it, and actually run it. This is what catches the staleness gotcha above and any enum/factory-table order mismatch — the formal test suite under `test/` won't, since it doesn't know about cases it was never written to check.
- Don't expose `QuantLib.Internal.*` modules (moving them from `other-modules` to `exposed-modules` in `package.yaml`) to work around a c2hs cross-module `{#import#}` ordering problem — this only comes up for **enum** types. Prefer avoiding it in the first place: add dedicated, specific constructors (e.g. `ActualActualBond' :: Schedule -> DayCounterConstructor`, hardcoding the enum value inside its own C++ shim function) rather than one generic constructor that takes the enum as an argument — see the `reconcile-daycounters` skill's `ActualActual` case. A first attempt at that case took the convention as a generic `ActualActualConvention` argument, which needed referencing that enum type (declared in `CalendarEnum.chs`) inside a `{#fun#}` binding in `Schedule.chs` — `{#import Module#}(Type)`, which needs the source module's `.chi` file to already exist, i.e. that module must be preprocessed first. This reliably failed since `CalendarEnum` lives in `other-modules` (confirmed: reordering within `other-modules`, and even fully serial `-j1` builds, did **not** fix it — `other-modules` isn't part of the ordered-by-list-position scheme the `exposed-modules` comment describes), and exposing the internal module is off the table. The dedicated-constructor design sidesteps this entirely — hardcoding the value per C++ function means no enum crosses a module boundary at all, so this doesn't come up unless a case genuinely needs a parameterized enum passed through (rare — prefer dedicated constructors first). If it's unavoidable: marshal that one field as a plain `Int`/`CInt` in the low-level, unexported `{#fun#}` glue binding only, converting via `fromEnum` at its one call site — the public constructor stays fully typed; only a private FFI-marshalling detail is affected. Pointer/foreign-type fields (like `Schedule` itself) never hit this at all — just locally re-declare a `{#pointer#}` for the type in the file that needs it, same as `Schedule`'s own `{#pointer *Schedule foreign -> CSchedule nocode#}` is already independently declared in several `.chs` files rather than imported cross-module.
- Don't export c2hs's raw, double-underscore-prefixed enum constructor names (e.g. `ActualActual__Bond` from `{#enum ActualActualConvention{} add prefix = "ActualActual__"#}`) through any public module — they read as internal/generated, not like the rest of the library's API. If a case needs to be user-facing, give it a proper dedicated constructor/name instead (see the point above) rather than exporting the enum type itself.
- When finishing a feature, check README.md's `# TODO` section for an item it resolves and remove it.
- We rarely bind inspector/getter methods beyond what scheduling/pricing/output actually needs — e.g. `Schedule` binds only `dates` out of ~20 upstream inspectors, `Calendar` binds none of its 4 pure inspectors (`empty()`/`name()`/`addedHolidays()`/`removedHolidays()`), and `Currency` binds a curated 5 of 10 rather than all of them. Setters are bound only for a few justified cases — engine/pricer wiring (`setPricingEngine`, `setCouponPricer(s)`), the global `Settings` singleton, and `SimpleQuote.setValue` (inherently mutable by design) — not as general field mutators. When a new field is genuinely needed, prefer adding a targeted getter (as with `FxForward`'s `fairForwardRate`/`npvSourceCurrency`/`npvTargetCurrency`) over binding every inspector the C++ class happens to expose, and prefer constructing a new object over mutating an existing one.
- Don't mirror QuantLib's C++ class hierarchy 1:1 in the Haskell layer. If a bound class has no calculations of its own and is never needed as an argument type elsewhere, it doesn't need a dedicated Haskell object/pointer type — a constructing function that builds and returns the parent (or grandparent) type directly is enough. This is already how pricing engines work: `discountingSwapEngine`, `blackCapFloorEngine`, etc. all return the generic `PricingEngine` type, not a dedicated `DiscountingSwapEngine`/`BlackCapFloorEngine` type, since nothing needs the more specific type back. Only introduce a dedicated type (as with `FxForward`'s `fairForwardRate`/`npvSourceCurrency`/`npvTargetCurrency`, or `ForwardRateAgreement`'s `forwardRate`) when the class actually has its own calc/getter or must be passed around as its own type. This applies to module *placement* too: group a new binding with its topically-related family (e.g. `FxForward` lives in `QuantLib/Instrument/Forward.chs` alongside `ForwardRateAgreement`/`BondForward`) rather than a generic hierarchy-root file, even when the C++ inheritance doesn't literally match.
